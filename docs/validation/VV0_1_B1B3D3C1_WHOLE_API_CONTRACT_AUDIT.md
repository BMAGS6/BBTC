## 1. Source-level call graph and ordering

The complete native-family functions are generated by `BBTC_VV_DEFINE_COMPARE`
in `comparison_api.c`. For each of the three native families, the relevant
control flow is:

1. Reject a null output without writing to it.
2. Set every *field value* of a nonnull result to its canonical failure state.
3. Reject a null policy or unsupported comparison method without examining
   floating-point values or touching the floating-point environment.
4. Call `feholdexcept` before floating-point validation.
5. Call `bbtc_vv_prepare_*` to validate and obtain an **exact finding**.
6. Only on a successful non-EXACT method, call `bbtc_vv_metric_exact_*` to
   construct an exact, unrounded rational diagnostic.
7. Only after successful rational construction, call
   `bbtc_vv_metric_round_*` to select its nearest-even native value and
   separate representability classification.
8. Restore the outer floating-point environment via `fesetenv`.
9. Return failure without publishing provisional fields, or commit all three
   result fields on success.

`bbtc_vv_prepare_*` in `comparison.c` maps the public comparison-method enum
explicitly to a different private dyadic enum. It holds/restores its own
nested environment and maps every dyadic failure to a non-success API status.
An unknown private status becomes `NUMERICAL_FAILURE`. No native rounded
error is involved in obtaining the finding.

The exact metric helper also uses an intentional nested `feholdexcept` guard,
as does the native rounding helper. Each call has its own restoration site.
Successful nested restoration leaves the enclosing held environment unchanged;
outer restoration returns the saved caller environment before any success
result is published.

## 2. Contract review: output and failure semantics (A02, A06, A07)

The outer comparison function has precisely one successful output commit,
after `fesetenv`. The output is first cleared by a typed structure compound
literal. C does **not** guarantee deterministic structure-padding bytes; only
the `finding`, `metric_state`, and `metric` field values are contractual.

Under successful evaluation, `prepare` maps the private Boolean to either
`BBTC_VV_FINDING_PASS` or `BBTC_VV_FINDING_FAIL`. No path constructs
`BBTC_VV_FINDING_INDETERMINATE`. The only permitted incomplete result is a
fully cleared result following a non-success operation status.

For the EXACT method, `metric_state` remains `NOT_COMPUTED` and the metric
remains +0. In ABSOLUTE and REFERENCE_RELATIVE modes, the rounded diagnostic
is calculated **only after** the exact Boolean. It cannot replace or revise
the previously obtained finding. `EXCEEDS_RANGE` and `ROUNDED_TO_ZERO` are
successfully classified diagnostics and do not manufacture an operation
failure or an indeterminate finding.

After the pointer and method checks, the admitted environment is established
before numeric classification. The private dyadic kernel tests **any NaN**
across reference, observation and tolerance before testing **any infinity**.
Only finite values reach the sign and tolerance checks. Exact tolerance
accepts either sign of zero and rejects nonzero tolerance; Absolute and
Reference-relative reject negative finite tolerance, and Relative rejects a
zero reference even if observation and tolerance are also zero.

After an exact-success finding, a subsequent unexpected metric or rounding
failure is translated into `NUMERICAL_FAILURE` unless the helper reported
`UNSUPPORTED_FP_ENVIRONMENT`. Such a failure still cannot publish the exact
finding on its own, because the outer result remains cleared.

## 3. Native precision and environment (A08, A09, A10, A11)

The macros expand into three **typed** APIs. The dyadic, metric and rounding
helpers use matching `frexpf`/`frexp`/`frexpl` and
`scalbnf`/`scalbn`/`scalbnl` operations rather than narrowing all inputs to
`double`. The supported numerical envelope is the qualified primary
binary32/binary64/padded-x87 profile with `FLT_EVAL_METHOD==0`; the previous
capability-hardening increment removed the unqualified binary64-backed
`long double` alternate gate.

The code rejects compilation with `__FAST_MATH__` or finite-math-only modes.
The independent host probe and acceptance campaign record the actual compiler
versions, storage and significand/exponent macros, four incoming rounding
modes, and a simple floating-point-environment preservation check. A matching
format macro is not, by itself, a universal runtime certificate.

For **supported normal returns**, every nested and outer guard attempts
restoration; successful outer `fesetenv` is a precondition of publishing a
result. Restoration failure is reported as `NUMERICAL_FAILURE` and leaves
result fields cleared. The source cannot guarantee an unchanged environment
when the platform's own `fesetenv` fails. The contract does not promise safe
behavior with unmasked traps, noncanonical extended encodings or arbitrary
compilers/CPUs. This test campaign cannot force failures of `feholdexcept`
or `fesetenv`; these branches require code-review evidence rather than a
claim that they were dynamically exercised.

## 4. New end-to-end directed regressions

`tests/validation/test_comparison_api.c` adds **nine** cmocka functions:
three native families multiplied by the following three test categories.
This extends the deterministic suite from 15 to **24** registered tests.

- **Status precedence and canonical failure:** structural method rejection
  outranks a nonfinite input; a NaN tolerance or NaN observation outranks an
  infinity; an infinite tolerance alone is nonfinite; `-0` is valid
  tolerance; zero-reference Relative fails; Exact accepts both signed zeros
  without computing a diagnostic. Every failure is checked field by field.
- **Diagnostic independence:** `|M-(-M)|=2M>M` must report a definitive FAIL
  and `EXCEEDS_RANGE`; the same inputs with Relative tolerance 2 yield a
  definitive PASS and exact diagnostic 2. The `2^p+1` adversary must FAIL
  against tolerance `2^p` even when its diagnostic rounds to `2^p`.
- **Floating-point preservation:** four incoming rounding modes combined
  with seven sticky-flag presets (including all five common flags together)
  are checked on Exact-success, inexact Relative-success and NaN-failure
  paths. The flag/mode snapshot is taken immediately after each API call.
  Each native family exercises 28 combinations and 84 calls in this test.

These additions do not replace the independent `fractions.Fraction` full-API
oracle, which must remain arithmetically independent from the C implementation.
Tests are evidence for specific paths, not proof of every possible execution.
