# BBTC External Ballistics Design Contract

**Contract version:** 0.2.2

**Project phase:** EB1.3

**Applies to:** `rewrite/eb1_3_analytic_propagation_v1`

**Status:** Accepted

**Date:** 2026-11-27

## 1. Purpose

This document defines the engineering architecture for external ballistics in
BMAGS' Ballistic Trajectory Calculator (BBTC).

The external-ballistics subsystem is designed as an independent C23 library
component suitable for standalone scientific use and direct integration into
Cubes of Honor.

This contract supplements the accepted
`docs/design/BBTC_DESIGN_CONTRACT.md`. Generic requirements defined by that
contract remain applicable unless this document explicitly replaces them for
external-ballistics work.

Internal ballistics is not a dependency of external ballistics. A caller MAY
supply a muzzle state produced by a BBTC internal-ballistics model, but the
external-ballistics API MUST also accept a complete caller-supplied initial
projectile state without requiring any internal-ballistics component.

The words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** state
requirements.

## 2. Architectural goals

The external-ballistics subsystem MUST:

- model projectile flight as a reusable physics library rather than as gameplay
  logic;
- support six-degree-of-freedom rigid-body dynamics from the architectural
  foundation;
- remain independent of Cubes of Honor source types and subsystems;
- integrate cleanly with Cubes of Honor through explicit adapter code;
- use SI units throughout its public physics API and computational core;
- retain BBTC's `float`, `double`, and `long double` scalar families;
- make reference-frame, orientation, and angular-velocity conventions explicit;
- obtain atmosphere and environmental state through caller-controlled
  interfaces rather than requiring a BBTC-owned world or weather system;
- separate numerical integration from aerodynamic force and moment models;
- permit progressively higher-fidelity physical models without changing the
  fundamental state representation; and
- preserve deterministic diagnostics and fail-closed validation behavior
  consistent with the existing BBTC design contract.

External-ballistics architecture MUST NOT assume that every consumer is a game,
that every consumer uses Earth, or that every initial projectile state was
generated by BBTC internal ballistics.

## 3. Ownership boundary

BBTC external ballistics owns:

- projectile rigid-body state;
- translational and rotational equations of motion;
- aerodynamic force and moment evaluation;
- relative-air velocity;
- Mach-dependent ballistic calculations;
- numerical integration of projectile state;
- applicable rotational, gyroscopic, aerodynamic, and reference-frame effects;
- numerical and physical-model diagnostics; and
- interpolation or trajectory-state information required to expose the
  calculated flight path.

The host application owns:

- world geometry;
- terrain and object collision;
- game entities;
- rendering;
- audiovisual effects;
- networking and replication;
- damage and gameplay consequences;
- world-unit conventions;
- atmospheric or weather simulation when supplied by the host; and
- conversion between host-specific types and BBTC public types.

BBTC MUST NOT depend on Cubes of Honor headers.

Cubes of Honor integration MUST occur through an adapter owned by Cubes of
Honor.

Relevant quantities include:

| Quantity | Canonical unit |
| --- | --- |
| Position / displacement | m |
| Velocity | m/s |
| Acceleration | m/s² |
| Time | s |
| Mass | kg |
| Force | N |
| Moment / torque | N·m |

| Pressure | Pa |

| Density | kg/m³ |

Host-specific units MUST be converted at the integration boundary.

## 5. Scalar precision

External ballistics MUST provide first-class native implementations for:

- `float`;
- `double`; and
- `long double`.

The scalar-family rules of the parent BBTC contract remain applicable.

The `double` family SHOULD remain the principal validation and reference family.

A performance-sensitive consumer such as Cubes of Honor MAY use the `float`
family, the `double` family, or another supported family through explicit
precision-qualified APIs.

The choice of runtime precision in Cubes of Honor MUST NOT alter the public ABI
of another BBTC precision family.

### 5.1 Mathematical value types

BBTC MUST own the mathematical value types required to state its public physics
contracts. The external-ballistics API MUST NOT depend on Cubes of Honor vector,
quaternion, matrix, or other engine-math declarations.

The first external-ballistics math boundary SHOULD remain deliberately small.
It MUST provide precision-qualified three-dimensional vector and quaternion
value records sufficient to represent projectile state, environmental vectors,
forces, moments, and orientations. Equivalent `float`, `double`, and
`long double` records MUST follow the scalar-family requirements of the parent
contract.

These BBTC records are physics-interface types, not the beginning of a competing
general-purpose graphics or game-engine mathematics library. Operations required
by the solver, such as vector addition, subtraction, scaling, dot products,
cross products, norms, normalization, quaternion products, conjugation,
normalization, and vector rotation, MAY remain internal implementation helpers
until a concrete public use justifies exposing them.

EB0 does not require a public four-by-four matrix abstraction. Rendering,
projection, camera, and scene-transform matrices remain host responsibilities.
Rigid-body inertia MUST be represented using physical moments or an explicitly
defined physical inertia tensor rather than by reusing a graphics-oriented
matrix type.

BBTC quaternion mathematics MUST use an active, right-handed Hamilton-product
convention. A BBTC orientation quaternion is written conceptually as
`q = (x, y, z, w)`, where `w` is the scalar component and `(x, y, z)` is the
vector component. For a unit world-from-body quaternion `q_WB`, a body-frame
vector `v_B` is rotated into the world/reference frame by the active rotation

`v_W = q_WB * (0, v_B) * inverse(q_WB)`.

For a unit quaternion, the inverse is the conjugate. Exact public record names,
declaration order, ABI layout, and which low-level operations are exposed remain
deferred to their dedicated EB0 implementation checkpoints.

A host MUST NOT replace BBTC mathematical types through preprocessor aliases,
build definitions, typedef substitution, or other configuration that changes
the meaning or ABI of the BBTC public headers.

### 5.2 Cubes of Honor precision and conversion boundary

Cubes of Honor currently uses float-oriented engine math, while BBTC supports
three native scalar families. This difference MUST be handled explicitly at the
adapter boundary rather than by coupling the two type systems.

The initial Cubes of Honor integration SHOULD use the BBTC `double` family for
projectile state and numerical integration unless profiling demonstrates that a
different family provides a material gameplay benefit. Cubes of Honor MAY
continue to use its existing `float` vectors, quaternions, matrices, atmosphere
records, rendering state, and collision data.

The Cubes of Honor adapter MUST perform explicit value conversion when data
crosses the boundary. For example, a Cubes of Honor `vec3f_t` supplied to a
BBTC `double` simulation is converted component-by-component to the
corresponding BBTC double vector. BBTC output needed by the game is converted
back explicitly to the host representation.

Such conversion helpers SHOULD be small, inlineable, deterministic functions.
Their performance SHOULD be measured if they ever appear material in profiling,
but layout coincidence MUST NOT be used as a reason to bypass the language type
system.

## 6. Reference-frame model

BBTC external ballistics uses an explicitly defined right-handed reference frame.

The BBTC core MUST NOT assign intrinsic geographic meanings such as east,
north, south, or up to the three coordinate axes.

A host adapter MAY map the BBTC reference frame directly to an application
coordinate system when their handedness and axis meanings are compatible.

Position and translational velocity are expressed in the active reference
frame.

The initial integration origin SHOULD normally be local to the projectile launch
state rather than an unnecessarily large absolute world coordinate.

For Cubes of Honor, the intended integration origin is the muzzle position.
BBTC therefore begins projectile displacement at or near the local origin, and
the Cubes of Honor adapter reconstructs world-space position from the stored
muzzle origin plus the BBTC displacement.

## 7. Rigid-body state

The six-degree-of-freedom architecture MUST represent at least:

- simulation time;
- three-dimensional position;
- three-dimensional translational velocity;
- orientation as a unit quaternion; and
- three-dimensional angular velocity.

Euler angles MUST NOT be used as the integrated orientation state.

The quaternion represents **world-from-body** orientation: it transforms a
vector expressed in projectile body coordinates into the active reference
frame.

Angular velocity is expressed in the **projectile body frame**.

Quaternion normalization and integration behavior MUST be specified and tested
before the first rotational integrator is accepted.

The exact public record names and field layout are deferred to a later EB0
implementation checkpoint.

## 8. Projectile body frame

The canonical BBTC projectile body frame is right-handed and uses the following
axis meanings:

- `+X` is forward, from the projectile center of mass toward the nose;
- `+Y` is body-right; and
- `+Z` is body-down.

Positive angular quantities follow the right-hand rule about their corresponding
positive body axes. The longitudinal or roll axis is `+X`, the pitch axis is
`+Y`, and the yaw axis is `+Z`.

This convention is selected for physical clarity and compatibility with common
rigid-body and flight-dynamics formulations. It is intentionally independent of
a host application's camera, renderer, model-authoring, or world-axis
conventions.

For an axisymmetric projectile whose center of mass lies on the longitudinal
axis, `Ixx` denotes the axial moment of inertia and `Iyy` and `Izz` denote the
transverse moments. An axisymmetric model may require `Iyy == Izz`, but the
architecture MUST NOT assume that equality for every future rigid body.

A host whose local forward direction differs from BBTC `+X` MUST perform one
explicit, documented basis conversion at the adapter boundary. Host conventions
MUST NOT leak into BBTC aerodynamic coefficient definitions or rigid-body
equations.

## 9. Projectile physical properties

The architecture MUST support rigid-body projectile properties sufficient for
six-degree-of-freedom dynamics, including:

- mass;
- center-of-mass-related geometry required by implemented models;
- moments of inertia;
- aerodynamic reference dimensions; and
- aerodynamic-model data.

An axisymmetric projectile MAY use an optimized representation based on axial
and transverse moments of inertia where physically appropriate.

The architecture MUST NOT prevent a later general inertia representation.

Aerodynamic coefficient models and projectile geometry MUST remain logically
separate from the integrated dynamic state.

## 10. Environmental sampling

External ballistics MUST obtain local environmental conditions through an
explicit caller-controlled interface.

The environment interface MUST be capable of supplying, as applicable:

- air temperature;
- absolute pressure;
- air density;
- local speed of sound; and
- wind velocity.

Sampling MUST accept projectile position and simulation time so that a host can
provide altitude-dependent, position-dependent, or time-dependent conditions.

The integrator MUST permit environmental sampling at derivative-evaluation
points, including intermediate integration stages. A host environment MUST NOT
be restricted to one sample per render frame or one sample per complete
integration step.

BBTC MUST NOT require Cubes of Honor's atmosphere implementation.

The Cubes of Honor adapter is expected to obtain atmospheric state from the
authoritative Cubes of Honor atmosphere subsystem and translate the result into
the corresponding BBTC environment sample.

A standalone BBTC application MAY provide constant-atmosphere, standard-
atmosphere, table-driven, or other environment-provider helpers. Such helpers
MUST remain optional clients of the same environment contract used by hosted
applications; the core external-ballistics solver MUST NOT require one specific
BBTC-owned atmosphere implementation.

## 11. Reference-frame acceleration and rotation

Gravity MUST be supplied through an explicit physical/reference-frame contract
rather than assumed to have a fixed hard-coded axis.

For EB0.1-B6 and later external-ballistics work, **gravitational acceleration**
means the physical gravitational-field acceleration acting at the projectile
sample point. It excludes centrifugal, Coriolis, Euler, reference-origin
translation, aerodynamic, contact/support, propulsion, and other separately
modeled accelerations. A host or helper that begins from effective/apparent
gravity MUST NOT pass that quantity as B6 gravitational acceleration unless the
included non-inertial contributions have first been removed consistently.

Terminology from external gravity, geodesy, navigation, or host systems MUST
NOT be trusted by name alone. A quantity described as local gravity, normal
gravity, apparent gravity, effective gravity, or a plumb-line acceleration may
include centrifugal or other frame-dependent contributions. Such a quantity
must be decomposed consistently before its gravitational-field component is
stored in the B6 gravitational-acceleration member.

The active BBTC reference frame may translate and rotate relative to an inertial
frame. Its origin acceleration, angular velocity, and angular acceleration are
therefore independent kinematic inputs rather than hidden properties of
gravity.

All B6 reference-frame vectors are expressed in the axes of the active BBTC
reference frame used by external-ballistics translational position and velocity.
The angular velocity is the angular velocity of the active reference frame
relative to an inertial frame, expressed in active-reference coordinates. The
angular acceleration is the inertial time derivative of that frame angular
velocity, likewise expressed in active-reference coordinates.

This permits the same BBTC solver architecture to represent Earth-like,
non-Earth, artificial, reduced-gravity, accelerating-platform, rotating-
habitat, and game-specific environments without assigning intrinsic geographic
meaning to the generic BBTC axes.

For a projectile with reference-frame position `r_R` and velocity `v_R`, a
future reviewed non-inertial-acceleration checkpoint MUST use the conventional
kinematic relation. Here `r_R` is the projectile position measured from the
active reference-frame origin and expressed in active-reference coordinates,
and `v_R` is the projectile velocity relative to that active frame, expressed
in the same coordinates. For the currently frozen rigid-body state contract,
these meanings correspond directly to the translational `position_m` and
`velocity_m_per_s` state vectors.

```text
a_noninertial_R =
    -a_origin_R
    -2 * omega_R x v_R
    -alpha_R x r_R
    -omega_R x (omega_R x r_R)
```

where:

- `a_origin_R` is the inertial acceleration of the active reference-frame
  origin, expressed in active-reference coordinates;
- `omega_R` is the angular velocity of the active reference frame relative to an
  inertial frame, expressed in active-reference coordinates; and
- `alpha_R` is the inertial angular acceleration of that reference frame,
  expressed in active-reference coordinates.

The four terms correspond respectively to reference-origin translation,
Coriolis acceleration, Euler acceleration, and centrifugal acceleration. The
formula is frozen here for sign and semantic consistency, but EB0.1-B6 does not
yet implement it.

A moving local-navigation frame does not require a separately named
"transport-rate force" when its complete translational acceleration, total
angular velocity relative to inertial space, and angular acceleration are
already represented by `a_origin_R`, `omega_R`, and `alpha_R`. A later
specialized helper MAY decompose those quantities into planetary rotation,
transport rate, curvature, or other convenient components, but the generic
solver consumes the total frame kinematics and MUST NOT double count a
decomposed contribution.

BBTC MUST support the physical behavior conventionally described as the
Eötvös effect for applicable Earth-like rotating-frame models. For a complete
Earth-fixed or Earth-related frame model, the velocity-dependent Eötvös
contribution MUST arise consistently from the Coriolis/reference-frame
kinematics and selected gravity treatment. An implementation MUST NOT add a
second empirical Eötvös correction when the same acceleration is already
represented by the generic rotating-frame formulation.

The B6 reference-frame origin is deliberately independent of any planetary
center. A local or muzzle-relative projectile position therefore remains a
local coordinate. For an Earth-fixed local frame, Earth-specific code may use
planetary radius, latitude, ellipsoid geometry, and Earth rotation to construct
the inertial acceleration of the local frame origin without forcing the generic
projectile state to contain an Earth-centered position vector.

Earth-specific helpers MAY construct B6 quantities from Earth rotation,
geographic orientation, latitude, planetary geometry, gravity models, or
equivalent data, but the generic BBTC core MUST NOT hard-code Earth constants,
Earth geography, WGS-84, or a particular planetary model.

Coriolis, centrifugal, Euler, Eötvös, or related non-inertial accelerations
MUST NOT be evaluated by the solver until the B6 value contract and the later
reference-frame sampling/provider boundary are independently reviewed and
tested.

## 12. Numerical architecture

The numerical integrator MUST be separable from the physical force and moment
model.

Conceptually, state evolution follows:

- translational position derivative from translational velocity;
- translational velocity derivative from physical applied force divided by mass
  plus separately represented acceleration contributions such as gravity and,
  where applicable, reviewed non-inertial reference-frame effects;
- rotational dynamics from applied moments and rigid-body inertia; and
- quaternion evolution from the defined orientation and angular-velocity
  convention.

For the frozen world-from-body orientation `q_WB` and body-frame angular
velocity `omega_B`, the quaternion differential equation uses the Hamilton
composition

`dq_WB/dt = 0.5 * q_WB * omega_B_quat`,

where `omega_B_quat` is the pure quaternion whose vector part is `omega_B` and
whose scalar part is zero. The first rotational implementation MUST validate
this convention independently rather than relying only on visually plausible
orientation behavior.

Quaternion normalization or constraint-control strategy MUST be documented and
tested. Renormalization MAY control ordinary numerical drift, but it MUST NOT be
used to silently accept a nonfinite, zero-length, or otherwise invalid
orientation supplied at a public validation boundary.

The first correctness-oriented implementation MAY use a fixed-step
fourth-order Runge-Kutta method.

Future adaptive, game-oriented, or specialized rotational integrators MUST be
able to use the same physical state and force/moment contracts without replacing
the external-ballistics architecture.

## 13. Cubes of Honor integration boundary

BBTC MUST remain usable as an ordinary standalone library through the
`bbtc::bbtc` CMake target.

Cubes of Honor SHOULD consume BBTC as a Git submodule and CMake subproject
rather than compiling BBTC source files directly into its own source list.

The Cubes of Honor adapter is responsible for:

- conversion between Cubes of Honor vector/quaternion types and BBTC types;
- conversion between Cubes of Honor world scale and SI meters;
- construction of the muzzle-relative initial state;
- sampling the Cubes of Honor atmosphere at the projectile location;
- supplying gravity and other reference-frame information;
- converting calculated BBTC positions back to Cubes of Honor world space; and
- passing calculated trajectory segments to Cubes of Honor collision systems.

The adapter MUST NOT type-pun or pointer-cast distinct Cubes of Honor and BBTC
structure types merely because their layouts happen to match.

Explicit field-wise conversion is required unless a future shared ABI contract
states otherwise.

### 13.1 Cubes of Honor math and basis adapter

Cubes of Honor and BBTC intentionally retain separate mathematical type systems.
The adapter MUST translate values between them; neither project is required to
adopt the other's complete math library.

The currently established Cubes of Honor local camera/player basis uses:

- `+X` as local right;
- `+Y` as local up; and
- `-Z` as local forward.

The BBTC projectile body basis defined by section 8 uses:

- `+X` as projectile forward;
- `+Y` as projectile right; and
- `+Z` as projectile down.

Therefore the fixed body-to-Cubes-of-Honor-local basis correspondence is:

- BBTC body `+X` maps to Cubes of Honor local `-Z`;
- BBTC body `+Y` maps to Cubes of Honor local `+X`; and
- BBTC body `+Z` maps to Cubes of Honor local `-Y`.

The adapter MAY represent this fixed basis transformation as a constant
quaternion, an equivalent orthonormal three-by-three rotation, or an explicitly
tested basis mapping. It MUST NOT scatter equivalent sign changes or axis
swizzles throughout projectile setup, atmosphere sampling, rendering, or
collision code.

If `q_WC` denotes a Cubes of Honor world-from-local orientation and `q_CB`
denotes the fixed Cubes-of-Honor-local-from-BBTC-body basis rotation, the
initial BBTC world-from-body orientation is conceptually

`q_WB = q_WC * q_CB`

under the Hamilton active-rotation convention frozen in section 5.1.

This composition MUST be verified with basis-vector tests. At minimum, tests
MUST prove that BBTC body forward, right, and down map to the expected Cubes of
Honor directions for identity and representative yaw/pitch orientations.

The initial world-frame projectile velocity SHOULD be constructed from the
physical muzzle-speed magnitude and the transformed BBTC body-forward direction,
rather than by embedding Cubes of Honor camera-axis assumptions in BBTC core
code.

Cubes of Honor matrix functionality remains available to the game for rendering
and scene transforms, but BBTC MUST NOT require `mat4f_t` or any equivalent
host matrix type to integrate projectile rigid-body motion.

## 14. Collision and termination

BBTC does not own Cubes of Honor collision detection.

The external-ballistics system SHOULD expose sufficient state or trajectory
segment information for a host to perform continuous or discrete collision
queries.

A collision reported by the host MAY terminate or otherwise alter the host's
simulation of the projectile, but BBTC MUST NOT acquire a dependency on voxel,
terrain, character, or other game-world geometry.

## 15. Initial implementation sequence

The intended staged implementation is:

1. EB0 — mathematical, state, frame, environment, and integration contracts;
2. EB1 — vacuum six-degree-of-freedom propagation and analytic validation;
3. EB2 — basic aerodynamic relative-air and drag models;
4. EB3 — aerodynamic attitude forces and moments;
5. EB4 — spin-stabilized and gyroscopic effects;
6. EB5 — expanded atmospheric and wind coupling;
7. EB6 — rotating-reference-frame effects where appropriate;
8. EB7 — higher-fidelity Mach-dependent and projectile-specific aerodynamic
   models.

Each stage MUST remain independently testable.

### 15.1 Required environment and reference-frame capability reconstruction

The reconstructed architecture MUST preserve the useful physical capabilities of
the pre-rewrite BBTC environment and six-degree-of-freedom work without copying
its former structural coupling or unverified equations.

Later reviewed checkpoints MUST provide an architectural path for:

- position-dependent, altitude-dependent, and time-dependent environment
  sampling;
- arbitrary world/reference-frame air-velocity fields, including spatially or
  temporally varying wind;
- optional standalone atmosphere models;
- optional humid-air modeling, including relative-humidity input and the
  thermodynamic calculations needed to obtain density and acoustic properties;
- optional standard-atmosphere or table-driven helpers;
- explicit gravity or gravity-field input;
- explicit planetary/reference-frame angular velocity;
- Earth-like rotation helpers without hard-coding Earth into the generic core;
- Coriolis acceleration;
- centrifugal acceleration;
- Euler acceleration when a modeled frame has time-varying angular velocity;
- transport-rate or curvature effects when a later moving local-frame model
  requires them; and
- analytically verified Earth-like behavior conventionally described as the
  Eötvös effect.

Legacy quantities such as saturation vapor pressure, water-vapor partial
pressure, dry-air partial pressure, vapor mass fraction, inverse speed of sound,
wind-direction angles, muzzle atmosphere values, altitude references, and
similar convenience or intermediate values MUST NOT automatically become fields
of the generic sampled-environment record. They belong in a concrete atmosphere
model, configuration record, derived calculation, or convenience helper unless
a later reviewed public contract demonstrates that generic solver state truly
requires them.

Environment-provider and atmosphere-model calculations MUST NOT require mutable
history merely to evaluate one position and time. In particular, an RK or other
multi-stage integrator must be able to request samples in derivative-stage order
without changing the physical answer because a previous sample mutated hidden
pressure, temperature, density, or altitude state.

The reference-frame implementation MUST prevent double counting between
supplied gravity and inertial terms. Earth/Eötvös validation MUST likewise
prevent a separately named correction from duplicating acceleration already
present in the mathematically complete rotating-frame formulation.

## 16. EB0.1-A acceptance criteria

EB0.1-A is complete when:

- external ballistics is formally defined as independent of internal ballistics;
- the existing generic BBTC library, precision, diagnostic, validation, and
  build rules are explicitly inherited;
- SI-only external-ballistics boundaries are frozen;
- BBTC owns minimal precision-qualified vector and quaternion value types without
  depending on Cubes of Honor math headers;
- BBTC mathematical value types cannot be replaced through host typedef aliases,
  preprocessor configuration, or ABI-changing build switches;
- EB0 requires no public graphics-oriented four-by-four matrix abstraction;
- the reference-frame architecture is right-handed without hard-coded
  geographic axis meanings;
- muzzle-relative/local-origin integration is adopted as the intended Cubes of
  Honor integration strategy;
- the BBTC projectile body frame is frozen as `+X` forward, `+Y` right, and
  `+Z` down;
- world-from-body quaternion semantics and active Hamilton rotation are frozen;
- body-frame angular-velocity semantics and the corresponding quaternion
  differential-equation multiplication order are frozen;
- environment sampling is caller-controlled, position-aware, and time-aware;
- environmental sampling is permitted at numerical derivative sub-stages;
- gravity and planetary/reference-frame rotation are supplied explicitly rather
  than hidden inside the solver;
- numerical integration is separated from aerodynamic force and moment models;
- Cubes of Honor is explicitly responsible for world scale, atmosphere,
  collision, rendering, networking, damage, and gameplay;
- Cubes of Honor integration uses an adapter rather than introducing CoH
  dependencies into BBTC;
- Cubes of Honor retains its existing vector, quaternion, and matrix math while
  crossing the BBTC boundary through explicit value conversions;
- the initial Cubes of Honor integration should use BBTC `double` unless later
  profiling justifies a different supported precision family;
- the fixed Cubes of Honor local-to-BBTC body-basis relationship is documented
  and requires basis-vector verification rather than scattered axis swizzles;
- exact public external-ballistics type names and structure layouts remain
  deferred until their dedicated implementation checkpoints;
- EB0.1-A introduces no external-ballistics public symbol or solver
  implementation; and
- this contract is reviewed and changed from `Draft` to `Accepted` before the
  first EB0 implementation checkpoint is committed.

## 17. EB0.1-B1 mathematical value and rigid-body state foundation

EB0.1-B1 is the first external-ballistics public-code checkpoint. It freezes
the value records required to represent three-dimensional vectors,
orientations, and one six-degree-of-freedom projectile state without yet
introducing vector operations, quaternion operations, state validation,
environment sampling, force or moment models, or numerical integration.

The purpose of this increment is deliberately narrow. Later external-ballistics
layers depend on these records, so their physical meaning and type identity
MUST be established and tested before equations begin to consume them.

### 17.1 Public header structure

The following public headers are introduced:

```text
include/bbtc/external_ballistics.h
include/bbtc/external_ballistics/vector.h
include/bbtc/external_ballistics/quaternion.h
include/bbtc/external_ballistics/state.h
```

`<bbtc/external_ballistics.h>` is the external-ballistics umbrella header and
MUST include the three concrete record headers. `<bbtc/bbtc.h>` MUST include
the external-ballistics umbrella so an ordinary BBTC consumer sees both the
existing API and the new EB0.1-B1 records.

The new headers MUST remain usable from ISO C23 and from the project's supported
C++ public-header compatibility test. No Cubes of Honor header may be required
to parse or use them.

### 17.2 Precision-qualified three-dimensional vectors

The public vector records are:

```c
bbtc_eb_vec3_float_t
bbtc_eb_vec3_double_t
bbtc_eb_vec3_long_double_t
```

Each record contains exactly the named scalar components `x`, `y`, and `z` in
that declaration order, expressed in the record's native scalar family.

The vector record itself carries no unit or coordinate-frame identity. Physical
meaning belongs to the field that contains the vector. For example, a
`position_m` field gives all three components metre semantics, while an
`angular_velocity_body_rad_per_s` field gives all three components body-frame
radians-per-second semantics.

This separation allows the same small vector representation to carry positions,
velocities, angular velocities, forces, moments, gravity, wind, and other
three-component physical quantities without creating one public structure type
for every possible unit.

EB0.1-B1 introduces representation only. No public arithmetic function is
required by this checkpoint.

### 17.3 Precision-qualified quaternions

The public quaternion records are:

```c
bbtc_eb_quat_float_t
bbtc_eb_quat_double_t
bbtc_eb_quat_long_double_t
```

Each record contains the vector components `x`, `y`, and `z`, followed by the
scalar component `w`, all in the matching native scalar family.

The component order matches the convention already frozen by section 5.1 and
is intentionally compatible with straightforward field-wise conversion to the
current Cubes of Honor quaternion representation. Type compatibility or
aliasing is NOT implied by matching component names or order.

A quaternion value record does not, by type alone, guarantee finite components,
unit length, or a physically valid orientation. Those requirements belong to
the future public state-validation contract. In particular, an all-zero
quaternion is representable but is not a valid orientation.

EB0.1-B1 introduces no public quaternion multiplication, normalization,
conjugation, vector-rotation, or interpolation function.

### 17.4 Precision-qualified rigid-body state

The first public six-degree-of-freedom state records are:

```c
bbtc_eb_rigid_body_state_float_t
bbtc_eb_rigid_body_state_double_t
bbtc_eb_rigid_body_state_long_double_t
```

Each state MUST contain the following fields:

```text
orientation_world_from_body
position_m
velocity_m_per_s
angular_velocity_body_rad_per_s
time_s
```

The declaration order above is frozen for EB0.1-B1. The quaternion is declared
first, followed by the three vector-valued members and then the scalar time.
This ordering keeps the largest composite member first and groups equal-sized
vector records together without changing any physical semantics.

`orientation_world_from_body` is the active world/reference-from-projectile-body
rotation defined by sections 5.1, 7, and 12. It is stored in the matching
`bbtc_eb_quat_*_t` type.

`position_m` is the projectile center-of-mass position in metres in the active
world/reference frame. In the intended Cubes of Honor adapter this position is
relative to the muzzle-local integration origin described by section 6.

`velocity_m_per_s` is the projectile center-of-mass translational velocity in
metres per second in the active world/reference frame.

`angular_velocity_body_rad_per_s` is the projectile angular-velocity vector in
radians per second expressed in the BBTC body frame defined by section 8.

`time_s` is simulation time in seconds measured from the external-ballistics
initial state.

The state record deliberately stores translational quantities in the active
world/reference frame while storing angular velocity in the body frame. Future
equations and validation MUST preserve that distinction explicitly.

A zero-initialized state is useful as deterministic storage but is not, by
itself, a valid projectile state because its quaternion is the all-zero
quaternion. EB0.1-B1 MUST NOT add an implicit identity-orientation fallback.

### 17.5 Ownership, ABI, and conversion rules

All EB0.1-B1 records are plain caller-owned values. They contain no pointers,
dynamic storage, hidden ownership, allocator state, reference counts, or host
application handles.

The records MUST NOT contain `vec3f_t`, `quatf_t`, `mat4f_t`, or another Cubes
of Honor type. The Cubes of Honor adapter performs explicit field-wise
conversion as required by sections 5.2 and 13.1.

No public alignment override is introduced by EB0.1-B1. Natural ISO C object
layout is used. The project MUST NOT freeze one universal byte size for these
records because scalar size and alignment are implementation properties,
especially for `long double`.

Tests MAY verify coherent layout properties on the current platform, but public
correctness MUST NOT depend on a particular padding pattern beyond the frozen
declaration and scalar-family semantics.

### 17.6 Deliberately deferred behavior

EB0.1-B1 does NOT define:

- vector arithmetic functions;
- quaternion arithmetic functions;
- quaternion normalization tolerance;
- rigid-body-state validation functions;
- environment-provider records or callbacks;
- gravity or planetary-rotation records;
- projectile mass, dimensions, or inertia records;
- force or moment accumulation;
- aerodynamic coefficients;
- numerical derivatives;
- an integration stepper; or
- Cubes of Honor adapter source code.

Those behaviors require their own reviewed contracts. Representation MUST be
established before algorithms begin assigning additional semantics to it.

## 19. EB0.1-B2 mathematical operations and state validation

EB0.1-B2 establishes the mathematical correctness layer required by later
external-ballistics dynamics. It adds a deliberately small internal
three-dimensional vector and quaternion operation set plus public validation of
the rigid-body state introduced by EB0.1-B1.

This checkpoint does NOT introduce projectile physical properties, atmosphere
sampling, force or moment models, derivatives of the rigid-body state, or a
numerical integrator. Its purpose is to make the coordinate and quaternion
machinery trustworthy before physical equations depend on it.

### 19.1 Legacy reconstruction constraints

The pre-rewrite BBTC external-ballistics implementation is a research reference,
not a normative source for the reconstructed API or conventions.

Useful legacy concepts MAY be reimplemented after independent verification,
including Hamilton quaternion multiplication, quaternion conjugation,
quaternion-vector rotation, vector cross products, and normalization.

Legacy behavior MUST NOT override the conventions already frozen by this
contract. In particular:

- the legacy orientation derivative used the multiplication order
  `omega_quat * q`;
- the reconstructed world-from-body orientation with body-frame angular
  velocity requires the later derivative contract to use `q * omega_body_quat`;
- the legacy quaternion normalizer silently left sufficiently small
  quaternions unchanged;
- the reconstructed implementation MUST report normalization failure rather
  than silently preserving or replacing an invalid quaternion; and
- no vector operation may combine operands expressed in different coordinate
  frames merely because their storage representations match.

EB0.1-B2 does not yet implement the quaternion orientation derivative. The
legacy multiplication-order discrepancy is recorded here so the later dynamics
checkpoint MUST test the frozen section 12 convention independently.

### 19.2 Internal mathematics boundary

The vector and quaternion operations introduced by EB0.1-B2 are implementation
support for BBTC physics and are NOT added to the public external-ballistics
API in this checkpoint.

The internal operation set MUST have native `float`, `double`, and
`long double` implementations. A family MUST NOT route arithmetic through
another scalar family.

The implementation MAY use a private internal header shared by BBTC source
files and dedicated internal tests. Such declarations are not public ABI and
MUST NOT be installed or included by `<bbtc/external_ballistics.h>`.

The internal operation set MUST NOT allocate dynamic storage, perform file I/O,
write diagnostics to standard streams, or depend on Cubes of Honor math types.

### 19.3 Internal three-dimensional vector operations

EB0.1-B2 MUST provide internal precision-qualified operations sufficient for:

- component-wise addition;
- component-wise subtraction;
- scalar multiplication;
- dot product;
- right-handed cross product;
- squared Euclidean norm;
- Euclidean norm; and
- normalization.

The right-handed cross product MUST satisfy the canonical basis relationships:

```text
+X cross +Y = +Z
+Y cross +Z = +X
+Z cross +X = +Y
```

and reversing either operand MUST reverse the result.

Norm and normalization implementations SHOULD avoid unnecessary overflow or
underflow where a standard-library scaling operation such as the appropriate
`hypot` family can provide a more robust result.

Vector normalization MUST be fail-closed. For the internal status-returning
normalization operation:

- a null input or output pointer returns `BBTC_STATUS_INVALID_ARGUMENT`;
- a NaN component returns `BBTC_STATUS_NAN_INPUT`;
- an infinite component returns `BBTC_STATUS_NONFINITE_INPUT`;
- a finite zero-length vector returns `BBTC_STATUS_OUTSIDE_DOMAIN`; and
- a finite nonzero vector produces a unit vector and
  `BBTC_STATUS_SUCCESS`.

On every failure for which a nonnull output pointer is available, the output
record MUST be cleared to all-zero components.

### 19.4 Internal quaternion operations

EB0.1-B2 MUST provide internal precision-qualified operations sufficient for:

- identity-quaternion construction;
- Hamilton multiplication;
- conjugation;
- squared Euclidean norm;
- Euclidean norm;
- normalization; and
- active rotation of a three-dimensional vector by a unit quaternion.

Quaternion multiplication MUST use the Hamilton product and MUST preserve
operand order. Quaternion multiplication is not commutative, and tests MUST
include at least one case for which `q1 * q2` and `q2 * q1` produce distinct
rotations.

The identity quaternion is:

```text
(x, y, z, w) = (0, 0, 0, 1)
```

Quaternion conjugation negates `x`, `y`, and `z` while preserving `w`.

For a unit quaternion `q` and vector `v`, active vector rotation MUST be
equivalent to:

`q * (0, v) * conjugate(q)`.

An optimized algebraically equivalent vector-rotation formula MAY be used by
the implementation, but tests MUST compare representative optimized results
against the explicit Hamilton-product definition.

Quaternion normalization MUST be fail-closed. For the internal
status-returning normalization operation:

- a null input or output pointer returns `BBTC_STATUS_INVALID_ARGUMENT`;
- a NaN component returns `BBTC_STATUS_NAN_INPUT`;
- an infinite component returns `BBTC_STATUS_NONFINITE_INPUT`;
- a finite zero-length quaternion returns `BBTC_STATUS_OUTSIDE_DOMAIN`; and
- a finite nonzero quaternion produces a unit quaternion and
  `BBTC_STATUS_SUCCESS`.

Normalization MUST NOT silently substitute the identity quaternion for an
invalid input.

On every failure for which a nonnull output pointer is available, the output
quaternion MUST be cleared to all-zero components.

### 19.5 Public rigid-body-state validation

EB0.1-B2 introduces the following public functions:

```c
bbtc_status_e
bbtc_eb_rigid_body_state_validate_float(
    const bbtc_eb_rigid_body_state_float_t* state
);

bbtc_status_e
bbtc_eb_rigid_body_state_validate_double(
    const bbtc_eb_rigid_body_state_double_t* state
);

bbtc_status_e
bbtc_eb_rigid_body_state_validate_long_double(
    const bbtc_eb_rigid_body_state_long_double_t* state
);
```

These functions validate caller-owned state without modifying it.

Validation MUST inspect:

- all four orientation-quaternion components;
- all three position components;
- all three translational-velocity components;
- all three body-angular-velocity components; and
- simulation time.

Finite position, translational velocity, and angular velocity may otherwise
have any sign or magnitude representable by the selected scalar family.

`time_s` MUST be greater than or equal to zero. Negative zero is accepted as
zero by the ordinary floating-point comparison semantics.

The orientation quaternion MUST be finite, nonzero, and sufficiently close to
unit length as defined by section 19.6.

The validator MUST NOT normalize, repair, clamp, replace, or otherwise mutate a
supplied state.

### 19.6 Orientation unit-norm acceptance tolerance

Public state validation compares the squared quaternion norm against one:

`abs(norm_squared - 1) <= tolerance`.

For EB0.1-B2, the acceptance tolerance for every scalar family is:

`64 * FLT_EPSILON`.

This common interoperability floor is intentional. Cubes of Honor currently
uses float-oriented quaternion math while the intended first BBTC integration
uses the native-double family. A quaternion that was normalized in float and
then converted component-by-component to double MUST NOT be rejected merely
because the double family can represent a much tighter normalization residual.

The tolerance is a validation boundary, not the arithmetic precision used by
the double or long-double solver families. Internal normalization and later
integration continue to use the native scalar family.

The validator MUST compute the norm in a manner that does not turn ordinary
finite near-unit inputs into false overflow or underflow failures.

A quaternion outside this tolerance returns `BBTC_STATUS_OUTSIDE_DOMAIN`.

This tolerance MAY be revised only through an explicit contract revision with
tests demonstrating the interoperability and numerical consequences.

### 19.7 Validation precedence

When more than one invalid condition exists in one rigid-body state, public
validation MUST apply the following deterministic precedence:

1. a null state pointer returns `BBTC_STATUS_INVALID_ARGUMENT`;
2. if any inspected scalar is NaN, return `BBTC_STATUS_NAN_INPUT`;
3. otherwise, if any inspected scalar is positive or negative infinity, return
   `BBTC_STATUS_NONFINITE_INPUT`;
4. otherwise, if `time_s` is negative, return
   `BBTC_STATUS_OUTSIDE_DOMAIN`;
5. otherwise, if the orientation quaternion is zero-length or outside the
   unit-norm acceptance tolerance, return `BBTC_STATUS_OUTSIDE_DOMAIN`;
6. otherwise return `BBTC_STATUS_SUCCESS`.

The NaN and infinity scans MUST cover the complete state before domain
conditions are evaluated. This prevents member declaration order from changing
the status reported for a multiply-invalid state.

### 19.8 Convention and interoperability tests

EB0.1-B2 tests MUST establish the mathematical conventions independently of
later ballistic behavior.

At minimum, tests MUST verify:

- right-handed cross-product basis identities and operand reversal;
- exact identity-quaternion behavior;
- Hamilton multiplication order with noncommuting rotations;
- conjugation;
- normalization success for representative nonunit finite values;
- normalization failure for zero, NaN, and infinity;
- active 90-degree basis rotations about each canonical positive axis;
- equivalence of `q` and `-q` as rotations;
- agreement between the optimized quaternion-vector rotation, if used, and the
  explicit `q * v * conjugate(q)` reference form;
- a unit quaternion passes rigid-body-state validation;
- zero orientation fails state validation;
- a materially nonunit orientation fails state validation;
- a quaternion within the section 19.6 tolerance passes validation;
- negative time fails validation;
- arbitrary finite signed position, velocity, and angular velocity are accepted;
- deterministic NaN-before-infinity-before-domain validation precedence; and
- all three precision families execute their own native arithmetic paths.

The Cubes of Honor basis relationship from section 13.1 MUST also be exercised
as a mathematical reference test. The unit quaternion

```text
(x, y, z, w) = (0.5, 0.5, -0.5, 0.5)
```

represents one valid active Cubes-of-Honor-local-from-BBTC-body basis rotation
under the frozen convention and MUST map:

```text
BBTC body +X -> Cubes of Honor local -Z
BBTC body +Y -> Cubes of Honor local +X
BBTC body +Z -> Cubes of Honor local -Y
```

Its negation MUST produce the same three rotated basis vectors.

This constant is a convention test vector, not a requirement that the future
Cubes of Honor adapter store or hard-code one particular quaternion sign.

### 19.9 Deliberately deferred behavior

EB0.1-B2 does NOT define or implement:

- quaternion orientation derivatives;
- rigid-body derivatives;
- projectile mass or inertia;
- aerodynamic reference geometry;
- environment samples or provider callbacks;
- gravity or rotating-reference-frame data;
- force or moment accumulation;
- aerodynamic coefficients or drag;
- RK4 or another numerical integrator; or
- Cubes of Honor adapter source code.

The later dynamics checkpoint MUST specifically test the section 12
`q_WB * omega_B_quat` orientation-derivative order rather than copying the
pre-rewrite `omega_quat * q` implementation.

## 21. EB0.1-B3 projectile physical properties and inertia

EB0.1-B3 freezes the public physical-property representation required to tell
later six-degree-of-freedom dynamics what rigid projectile is being propagated.
It introduces mass, diagonal principal-axis inertia, and aerodynamic reference
geometry without introducing aerodynamic coefficients, environmental state,
force or moment evaluation, state derivatives, or numerical integration.

The purpose of this checkpoint is to separate immutable projectile identity from
the time-varying rigid-body state defined in section 17.4. Projectile properties
MUST NOT be embedded in each integrated state merely because later equations
consume both.

### 21.1 Scope and body-origin convention

For EB0.1-B3, the origin of the canonical BBTC projectile body frame is the
projectile center of mass.

Consequently:

- `position_m` in the rigid-body state remains the world/reference-frame
  position of the center of mass;
- the principal moments introduced by this checkpoint are taken about axes
  through the center of mass;
- no separate center-of-mass offset is stored in the projectile-properties
  record; and
- a future aerodynamic center, center of pressure, or other force-application
  point is expressed as a body-frame offset from the center of mass if and when
  the corresponding force/moment model is introduced.

EB0.1-B3 MUST NOT introduce an aerodynamic-center offset merely to preserve the
shape of the pre-rewrite `SixDOFSpecs` record. Such model-specific geometry is
deferred until a force/moment checkpoint establishes its physical meaning.

### 21.2 Public header and precision-qualified types

EB0.1-B3 introduces:

```text
include/bbtc/external_ballistics/projectile.h
```

The external-ballistics umbrella header MUST expose that header after the
implementation checkpoint is accepted.

The public principal-inertia records are:

```c
bbtc_eb_principal_inertia_float_t
bbtc_eb_principal_inertia_double_t
bbtc_eb_principal_inertia_long_double_t
```

The public projectile-property records are:

```c
bbtc_eb_projectile_properties_float_t
bbtc_eb_projectile_properties_double_t
bbtc_eb_projectile_properties_long_double_t
```

All three families MUST use their native scalar type. No family may store or
validate its public values by converting the record to another scalar family.

### 21.3 Principal-inertia representation

Each `bbtc_eb_principal_inertia_*_t` record contains exactly the following
fields in this declaration order:

```text
moment_about_x_kg_m2
moment_about_y_kg_m2
moment_about_z_kg_m2
```

These are the diagonal principal moments of inertia about the canonical BBTC
body axes through the center of mass:

- `moment_about_x_kg_m2` is `Ixx`, the moment about body `+X`, the
  longitudinal/roll axis;
- `moment_about_y_kg_m2` is `Iyy`, the moment about body `+Y`, the pitch axis;
  and
- `moment_about_z_kg_m2` is `Izz`, the moment about body `+Z`, the yaw axis.

The EB0.1-B3 diagonal representation therefore applies to projectiles for which
the canonical BBTC body axes are principal axes at the center of mass. This is
appropriate for the intended spin-stabilized projectile use case and still
permits unequal `Ixx`, `Iyy`, and `Izz`.

An axisymmetric projectile will ordinarily have equal transverse moments,
`Iyy == Izz`, but public validation MUST NOT require that equality. Non-
axisymmetric rigid bodies with diagonal inertia in the canonical body frame are
valid EB0.1-B3 inputs.

A later checkpoint MAY add a full symmetric inertia tensor or another more
general representation. The B3 API MUST NOT claim that every future BBTC rigid
body is diagonal or axisymmetric.

### 21.4 Projectile-property record

Each `bbtc_eb_projectile_properties_*_t` record contains exactly the following
fields in this declaration order:

```text
principal_inertia
mass_kg
reference_diameter_m
reference_area_m2
```

`principal_inertia` uses the matching precision-qualified
`bbtc_eb_principal_inertia_*_t` record.

`mass_kg` is the projectile mass in kilograms and is independent of the
time-varying rigid-body state.

`reference_diameter_m` is a positive aerodynamic/reference diameter in metres.
For an ordinary round bullet this will normally be the physical bullet diameter,
but the field is a model reference dimension rather than a complete shape
description.

`reference_area_m2` is a positive aerodynamic/reference area in square metres.
It is the area to which future dimensionless aerodynamic coefficients may be
normalized.

EB0.1-B3 deliberately stores both reference diameter and reference area as
explicit physical-model reference quantities. The library MUST NOT silently
derive one from the other, MUST NOT assume a circular relation
`area = pi * diameter^2 / 4`, and MUST NOT reject a positive finite pair merely
because it does not satisfy that relation.

The caller and any later aerodynamic model are responsible for using reference
dimensions that are consistent with the coefficient convention being supplied.
A future convenience constructor for ordinary circular bullets MAY derive one
quantity from the other, but such a helper is outside B3 and MUST remain an
explicit operation rather than hidden validation behavior.

The B3 property record is not a complete projectile-shape model. Ogive, boat-
tail, meplat, bearing-surface, length, center-of-pressure, and material-
distribution descriptions remain deferred until a demonstrated physical model
requires them.

### 21.5 Physical validity requirements

A valid projectile-property record MUST satisfy all of the following:

- every scalar in the record is finite;
- `mass_kg > 0`;
- every principal moment of inertia is greater than zero;
- `reference_diameter_m > 0`;
- `reference_area_m2 > 0`; and
- the three principal moments satisfy the rigid-body inertia triangle
  inequalities:

```text
Ixx <= Iyy + Izz
Iyy <= Ixx + Izz
Izz <= Ixx + Iyy
```

Equality is permitted by the B3 contract. The validator MUST NOT add an
axisymmetry requirement and MUST NOT infer missing moments from another moment.

Implementations SHOULD evaluate the triangle inequalities in a manner that does
not create a false validation result solely because adding two very large
finite moments overflows the selected scalar family.

A zero-initialized projectile-property record is deterministic storage but is
invalid because its mass, reference dimensions, and principal moments are zero.

### 21.6 Public projectile-property validation

EB0.1-B3 introduces the following public functions:

```c
bbtc_status_e
bbtc_eb_projectile_properties_validate_float(
    const bbtc_eb_projectile_properties_float_t* properties
);

bbtc_status_e
bbtc_eb_projectile_properties_validate_double(
    const bbtc_eb_projectile_properties_double_t* properties
);

bbtc_status_e
bbtc_eb_projectile_properties_validate_long_double(
    const bbtc_eb_projectile_properties_long_double_t* properties
);
```

These functions are read-only and validate the complete caller-owned property
record.

The validator MUST NOT clamp, repair, derive, normalize, substitute, or mutate
any supplied property. In particular, it MUST NOT:

- replace zero or invalid inertia with a default value;
- force `Iyy` and `Izz` to equality;
- derive reference area from reference diameter;
- derive reference diameter from reference area; or
- substitute a default projectile mass or geometry.

### 21.7 Validation precedence

When more than one invalid condition exists in one projectile-property record,
validation MUST apply the following deterministic precedence:

1. a null properties pointer returns `BBTC_STATUS_INVALID_ARGUMENT`;
2. if any inspected scalar is NaN, return `BBTC_STATUS_NAN_INPUT`;
3. otherwise, if any inspected scalar is positive or negative infinity, return
   `BBTC_STATUS_NONFINITE_INPUT`;
4. otherwise, if mass, any principal moment, reference diameter, or reference
   area is not strictly greater than zero, return
   `BBTC_STATUS_OUTSIDE_DOMAIN`;
5. otherwise, if any principal-moment triangle inequality is violated, return
   `BBTC_STATUS_OUTSIDE_DOMAIN`;
6. otherwise return `BBTC_STATUS_SUCCESS`.

The NaN and infinity scans MUST cover the complete property record before
physical-domain checks are evaluated so declaration order cannot change the
reported status for a multiply-invalid input.

### 21.8 Ownership, ABI, and layout rules

B3 records are plain caller-owned values. They contain no pointers, dynamic
storage, allocator state, host handles, aerodynamic tables, callbacks, or
Cubes of Honor types.

No public alignment override is introduced. Natural ISO C object layout is used
and no universal byte size or padding pattern is frozen.

The `principal_inertia` composite is declared before the scalar members of the
projectile-property record. This preserves the project's deliberate
largest-composite-first declaration style while all scalar members within a
precision family retain their native scalar representation.

Callers MUST use the named members and documented semantics rather than
depending on incidental padding, `sizeof` values from another implementation,
or type-punning between precision families.

### 21.9 Required tests

EB0.1-B3 tests MUST verify at least:

- native scalar-family field types for all three principal-inertia records;
- native scalar-family field types and matching nested inertia type for all
  three projectile-property records;
- the exact field names and declaration order frozen by sections 21.3 and 21.4;
- acceptance of representative valid axisymmetric projectile properties;
- acceptance of representative valid non-axisymmetric diagonal inertia;
- rejection of zero and negative mass;
- rejection of zero and negative principal moments;
- rejection of zero and negative reference diameter and area;
- acceptance of principal moments that satisfy a triangle inequality at
  equality;
- rejection of each possible principal-moment triangle-inequality violation;
- acceptance of positive finite reference diameter and area without imposing a
  hidden circular-area relation;
- deterministic NaN-before-infinity-before-domain validation precedence;
- read-only validation behavior;
- all three precision-qualified validation functions;
- C and C++ public-header compatibility;
- independent-consumer visibility through the existing BBTC public umbrella;
  and
- continued success of the existing strict compiler and sanitizer gates.

### 21.10 Deliberately deferred behavior

EB0.1-B3 does NOT define or implement:

- aerodynamic coefficients such as `Cd`, `Cl`, or `Cm`;
- drag, lift, Magnus, spin-damping, yaw-of-repose, or tilt models;
- coefficient tables or Mach interpolation;
- aerodynamic-center, center-of-pressure, or other force-application offsets;
- a detailed projectile shape or material-distribution model;
- environment samples or environment-provider callbacks;
- gravity or rotating-reference-frame data;
- force or moment accumulation;
- rigid-body state derivatives;
- quaternion orientation derivatives;
- RK4 or another numerical integrator;
- collision behavior; or
- Cubes of Honor adapter source code.

The pre-rewrite `SixDOFSpecs.areaOverMass` value MUST NOT be copied as stored
public state. Any later area-to-mass ratio is a derived quantity from validated
B3 properties and SHOULD be computed where the consuming model makes that
derivation explicit.

## 23. EB0.1-B4 local environment sample and validation

EB0.1-B4 establishes the first public external-ballistics representation of one
already-sampled local atmospheric/environment state. The record is deliberately
separate from the mechanism that obtains it. It is a value passed to later
physics layers, not an atmosphere model, weather system, callback, cache, or
world object.

The purpose of this checkpoint is to freeze the data semantics that future
relative-air, Mach, aerodynamic, and derivative calculations will consume
without yet coupling those calculations to any specific environment provider.

### 23.1 Scope and sampling boundary

An EB0.1-B4 environment sample represents local conditions at one conceptual
projectile position and simulation time. The sample itself does NOT store that
position or time; those values belong to the state and to the future sampling
interface that requests an environment sample.

The record MUST be usable whether its values came from:

- a constant standalone atmosphere;
- a standard-atmosphere implementation;
- a table or measured data set;
- a Cubes of Honor atmosphere/weather subsystem;
- another host-controlled model; or
- an exact vacuum representation.

EB0.1-B4 defines only the sampled value record and its validation contract.
The callback/provider mechanism required by section 10 remains a separate
checkpoint.

### 23.2 Public header and precision-qualified types

EB0.1-B4 introduces:

```text
include/bbtc/external_ballistics/environment.h
```

The external-ballistics umbrella header MUST include this public header.

The precision-qualified sample records are:

```c
bbtc_eb_environment_sample_float_t
bbtc_eb_environment_sample_double_t
bbtc_eb_environment_sample_long_double_t
```

Each family MUST use its native scalar type directly. No precision family may
store or validate its fields by routing them through another scalar family.

The matching public validators are:

```c
bbtc_eb_environment_sample_validate_float
bbtc_eb_environment_sample_validate_double
bbtc_eb_environment_sample_validate_long_double
```

### 23.3 Environment-sample record

Each precision family MUST contain the following fields in this exact
declaration order:

```text
air_velocity_world_m_per_s
temperature_k
absolute_pressure_pa
air_density_kg_per_m3
speed_of_sound_m_per_s
```

`air_velocity_world_m_per_s` uses the matching `bbtc_eb_vec3_*_t` type and is
declared first so the composite value precedes the equal-size scalar members.
No public alignment override is introduced.

### 23.4 Field semantics

`air_velocity_world_m_per_s` is the velocity of the local atmospheric medium,
in metres per second, expressed in the same active world/reference frame used
by `bbtc_eb_rigid_body_state_*_t.velocity_m_per_s`.

For an Earth-like host this quantity is commonly described as wind velocity.
The field is named in terms of the moving medium rather than projectile-relative
airspeed because future relative-air calculations MUST derive the latter
explicitly from projectile and environment state. Conceptually:

`v_relative_air_W = v_projectile_W - v_air_W`.

EB0.1-B4 does NOT yet expose that derived operation.

`temperature_k` is local absolute thermodynamic temperature in kelvin.

`absolute_pressure_pa` is local absolute static pressure in pascals.

`air_density_kg_per_m3` is local atmospheric-medium mass density in kilograms
per cubic metre.

`speed_of_sound_m_per_s` is the local acoustic propagation speed in metres per
second used by future Mach-number calculations.

These quantities are caller-supplied model outputs. BBTC MUST NOT silently
derive density from pressure and temperature, derive pressure from density and
temperature, or derive speed of sound from another thermodynamic relation at
this validation boundary.

### 23.5 Vacuum and thermodynamic-consistency policy

Exact vacuum MUST be representable.

A canonical exact-vacuum sample uses:

```text
absolute_pressure_pa      = 0
air_density_kg_per_m3     = 0
speed_of_sound_m_per_s    = 0
```

`temperature_k` MUST still be positive and finite because the record retains a
well-defined scalar value rather than introducing a conditional or optional
temperature representation.

`air_velocity_world_m_per_s` MAY contain any finite vector in vacuum. No
aerodynamic model may assign physical influence to that vector when the medium
density is zero.

A zero speed of sound is valid only when `air_density_kg_per_m3` is zero.
Any positive-density medium MUST therefore provide a strictly positive finite
speed of sound.

When `air_density_kg_per_m3` is zero, future aerodynamic calculations MUST
recognize the vacuum condition before attempting Mach-number normalization.
They MUST NOT divide relative-air speed by a zero speed of sound merely to
produce a nominal Mach value. In exact vacuum, aerodynamic force and moment
models have no medium from which to produce aerodynamic loading.

Because EB0.1-B4 deliberately imposes no equation of state, validation alone
does not classify every zero-density record as canonical exact vacuum. For
example, a caller may supply zero density together with a nonzero pressure
without violating the individual B4 field domains. Such cross-field physical
consistency remains the responsibility of the environment provider. A caller
intending to represent exact vacuum SHOULD use the canonical zero-pressure,
zero-density, zero-sound-speed representation above.

EB0.1-B4 MUST NOT impose an ideal-gas equation, a standard-atmosphere relation,
or another cross-field equation-of-state consistency test. In particular,
validation does not attempt to prove that pressure, density, temperature, and
speed of sound came from one specific thermodynamic model. That consistency is
owned by the caller or environment provider.

### 23.6 Physical validity requirements

A valid environment sample MUST satisfy all of the following:

- every scalar component of `air_velocity_world_m_per_s` is finite;
- `temperature_k` is finite and strictly greater than zero;
- `absolute_pressure_pa` is finite and greater than or equal to zero;
- `air_density_kg_per_m3` is finite and greater than or equal to zero;
- `speed_of_sound_m_per_s` is finite and greater than or equal to zero; and
- when `air_density_kg_per_m3` is greater than zero,
  `speed_of_sound_m_per_s` is strictly greater than zero.

The three air-velocity components may be positive, negative, or zero.

A zero-initialized environment sample is deterministic storage but is invalid
because `temperature_k == 0`.

### 23.7 Public validation and deterministic precedence

Validation is read-only and MUST NOT:

- clamp temperature, pressure, density, sound speed, or velocity;
- substitute a standard atmosphere;
- derive one thermodynamic field from another;
- replace a vacuum sample with small positive values;
- zero wind in vacuum; or
- mutate caller-owned storage.

For each precision family the validator MUST use this failure precedence:

1. a null sample pointer returns `BBTC_STATUS_INVALID_ARGUMENT`;
2. otherwise, if any inspected scalar is NaN, return `BBTC_STATUS_NAN_INPUT`;
3. otherwise, if any inspected scalar is infinite, return
   `BBTC_STATUS_NONFINITE_INPUT`;
4. otherwise, if any physical-domain rule in section 23.6 is violated, return
   `BBTC_STATUS_OUTSIDE_DOMAIN`; and
5. otherwise return `BBTC_STATUS_SUCCESS`.

NaN and infinity detection MUST scan the complete record before physical-domain
checks so multiply-invalid inputs do not change status merely because of member
declaration order.

### 23.8 Ownership, ABI, and layout rules

The environment sample is a plain caller-owned value. It MUST contain no:

- dynamic storage;
- pointers;
- callbacks;
- allocator state;
- host application handles;
- Cubes of Honor types; or
- hidden environment-provider ownership.

Natural ISO C object layout is used. No universal `sizeof` value, padding
pattern, or stronger-than-natural alignment is frozen.

The exact field order in section 23.3 is public contract, but consumers MUST
access named members rather than type-punning, assuming foreign layout
compatibility, or depending on incidental padding.

### 23.9 Required tests

EB0.1-B4 tests MUST verify at least:

- native field and nested vector types for all three scalar families;
- exact public member names and declaration order without freezing one byte
  size or padding pattern;
- a representative positive-density atmosphere sample is valid;
- positive, negative, and zero air-velocity components are accepted;
- the canonical exact-vacuum sample is valid;
- zero-initialized storage is invalid;
- zero and negative temperature are rejected;
- negative absolute pressure is rejected;
- negative density is rejected;
- negative speed of sound is rejected;
- zero speed of sound is rejected when density is positive;
- validation does not impose an ideal-gas or standard-atmosphere relation among
  otherwise individually valid fields;
- NaN has deterministic precedence over infinity and physical-domain errors;
- infinity has deterministic precedence over physical-domain errors;
- validation is read-only;
- native `float`, `double`, and `long double` entry points are independently
  exercised;
- the new public header remains usable from C++ through the project compatibility
  test;
- an independent CMake consumer can construct and validate a native-double
  sample through `<bbtc/bbtc.h>`; and
- existing normal, strict-warning, AddressSanitizer, and UndefinedBehaviorSanitizer
  gates remain green.

### 23.10 Deliberately deferred behavior

EB0.1-B4 does NOT define:

- an environment-provider callback or context object;
- position/time sampling dispatch;
- interpolation or caching;
- a BBTC-owned standard atmosphere;
- gravity;
- planetary or reference-frame angular velocity;
- relative-air-velocity helper functions;
- Mach-number evaluation;
- dynamic pressure;
- Reynolds number or viscosity;
- aerodynamic coefficients;
- drag, lift, Magnus, spin damping, or aerodynamic moments;
- force or moment accumulation;
- rigid-body state derivatives;
- numerical integration;
- collision behavior; or
- Cubes of Honor adapter source code.

Those behaviors require later reviewed checkpoints built on top of the sampled
value semantics frozen here.

## 25. EB0.1-B5 environment-provider interface

EB0.1-B5 establishes the caller-controlled mechanism that obtains the local
environment sample defined by EB0.1-B4 at an arbitrary projectile position and
simulation time.

This checkpoint deliberately separates provider dispatch from any particular
atmosphere model. A provider may represent a constant atmosphere, an analytic
model, a table, a Cubes of Honor weather subsystem, a vacuum, or another
caller-owned source. The generic BBTC solver consumes only the resulting B4
sample.

### 25.1 Sampling inputs

An environment-provider request is defined by:

- projectile center-of-mass position in metres, expressed in the active BBTC
  world/reference frame; and
- simulation time in seconds measured from the external-ballistics initial
  state.

The provider MUST NOT require projectile velocity, orientation, angular
velocity, mass, inertia, aerodynamic coefficients, or gameplay state merely to
determine the local atmospheric sample.

Position components MUST be finite. Sampling time MUST be finite and greater
than or equal to zero.

The provider interface MUST be usable at numerical derivative-evaluation
points. A future integrator may therefore sample at intermediate positions and
times and MAY invoke a provider more than once per complete integration step.

### 25.2 Public header and precision-qualified callback types

EB0.1-B5 introduces:

```text
include/bbtc/external_ballistics/environment_provider.h
```

The external-ballistics umbrella header MUST include this public header.

The precision-qualified callback types are:

```c
bbtc_eb_environment_provider_float_fn
bbtc_eb_environment_provider_double_fn
bbtc_eb_environment_provider_long_double_fn
```

Conceptually, each callback has the native-family form:

```c
bbtc_status_e callback(
    const void* context,
    const bbtc_eb_vec3_*_t* position_world_m,
    SCALAR time_s,
    bbtc_eb_environment_sample_*_t* out_sample
);
```

The exact callback parameter order above is frozen by EB0.1-B5.

The matching provider descriptor records are:

```c
bbtc_eb_environment_provider_float_t
bbtc_eb_environment_provider_double_t
bbtc_eb_environment_provider_long_double_t
```

Each descriptor contains the following fields in this exact declaration order:

```text
sample
context
```

`sample` is the matching precision-qualified callback pointer.

`context` is a borrowed `const void*` supplied unchanged to the callback. A
null context pointer is valid. BBTC does not allocate, free, retain, clone, or
interpret context storage.

No public alignment override is introduced.

### 25.3 Provider dispatch functions

BBTC exposes the following precision-qualified dispatch functions:

```c
bbtc_eb_environment_provider_sample_float
bbtc_eb_environment_provider_sample_double
bbtc_eb_environment_provider_sample_long_double
```

Conceptually, each function has the native-family form:

```c
bbtc_status_e bbtc_eb_environment_provider_sample_*(
    const bbtc_eb_environment_provider_*_t* provider,
    const bbtc_eb_vec3_*_t* position_world_m,
    SCALAR time_s,
    bbtc_eb_environment_sample_*_t* out_sample
);
```

The dispatch function, rather than future solver code, owns common provider
boundary validation and B4 output validation.

### 25.4 Callback contract

A provider callback returning `BBTC_STATUS_SUCCESS` MUST have fully initialized
every named field of `out_sample` with one complete B4 environment sample.

A provider callback returning any non-success BBTC status communicates sampling
failure. The dispatch layer MUST propagate that status unchanged after restoring
the public fail-closed output state described in section 25.5.

Callbacks MUST NOT depend on being invoked exactly once per integration step,
once per render frame, or in monotonically increasing position or time order.

Within one deterministic simulation snapshot, a provider MUST behave as a
function of its explicit position, time, and context rather than requiring the
result of a previous provider invocation. Internal caching MAY be used only when
it is observationally equivalent to this rule.

BBTC does not serialize provider callbacks. If caller-owned context refers to
mutable or shared state, the caller/provider implementation owns any required
synchronization and snapshot semantics.

### 25.5 Dispatch validation, output state, and precedence

`out_sample` is a required caller-owned output pointer.

If `out_sample` is null, dispatch MUST return `BBTC_STATUS_INVALID_ARGUMENT`;
no output-state guarantee is possible because no output object exists.

When `out_sample` is non-null, the dispatch function MUST establish the
all-zero B4 sample as the deterministic failure state of `*out_sample` before
validating any remaining input or invoking the callback.

For every subsequent dispatch failure, including invalid request data, provider
rejection, or invalid callback output, `*out_sample` MUST contain the all-zero
B4 sample on return. That zero value is intentionally deterministic storage and
remains invalid as a successful B4 atmospheric sample because its temperature
is zero.

The dispatch function MUST use this validation and failure order:

1. null provider, null provider callback, null position pointer, or null output
   pointer returns `BBTC_STATUS_INVALID_ARGUMENT`;
2. otherwise, if any position component or `time_s` is NaN, return
   `BBTC_STATUS_NAN_INPUT`;
3. otherwise, if any position component or `time_s` is infinite, return
   `BBTC_STATUS_NONFINITE_INPUT`;
4. otherwise, if `time_s` is negative, return `BBTC_STATUS_OUTSIDE_DOMAIN`;
5. otherwise invoke the provider callback exactly once;
6. if the callback returns a non-success status, return that status unchanged;
7. otherwise validate the callback-produced sample with the matching EB0.1-B4
   validator;
8. if sample validation fails, restore the all-zero failure sample and return
   the B4 validator status; and
9. otherwise return `BBTC_STATUS_SUCCESS` and preserve the validated callback
   output.

The callback MUST NOT be invoked when dispatch rejects the request in steps 1
through 4.

### 25.6 Precision and ABI rules

Each provider family operates entirely in its native scalar family:

- float position, time, callback, provider record, and B4 sample;
- double position, time, callback, provider record, and B4 sample; and
- long-double position, time, callback, provider record, and B4 sample.

Dispatch MUST NOT convert through another precision family.

Provider descriptors are plain borrowed-interface values. They contain no
owned allocation, reference count, host handle with BBTC-defined lifetime, or
Cubes of Honor type.

Function-pointer representation, object-pointer representation, padding, and
universal byte size are implementation properties and are not frozen beyond the
named member order and C type identities stated by this contract.

### 25.7 Cubes of Honor boundary

Cubes of Honor MAY implement an EB0.1-B5 provider callback whose context points
to caller-owned atmosphere or weather-query state.

The adapter MUST convert the BBTC world/reference position and simulation time
to whatever coordinates or query inputs the authoritative Cubes of Honor
atmosphere requires and must convert the resulting atmospheric values back into
the matching B4 environment sample.

BBTC MUST NOT include Cubes of Honor headers or assume that the provider context
has any particular host representation.

### 25.8 Required tests

EB0.1-B5 tests MUST verify at least:

- exact native callback signatures for float, double, and long double;
- exact provider descriptor member names and declaration order;
- native precision is preserved across position, time, and output sample;
- a null context is valid;
- null provider, callback, position, and output pointers are rejected;
- NaN position or time is rejected before callback invocation;
- infinite position or time is rejected before callback invocation;
- negative time is rejected before callback invocation;
- a valid request invokes the callback exactly once;
- the callback receives the exact context pointer, position components, and time
  supplied to dispatch;
- callback failure status is propagated unchanged;

  the all-zero fail-closed state;
- callback failure leaves the output in the all-zero fail-closed state;
- callback success with an invalid B4 sample returns the corresponding B4
  validation status and restores the all-zero failure state;
- callback success with a valid B4 sample preserves that sample;
- repeated and deliberately out-of-order requests work with a provider that does
  not depend on call history;
- float, double, and long-double dispatch entry points are exercised;
- the public header remains usable from C++;

- normal, strict-warning, AddressSanitizer, and UndefinedBehaviorSanitizer gates
  remain green.

### 25.9 Deliberately deferred behavior

EB0.1-B5 does NOT define:

- a BBTC-owned standard atmosphere;
- humid-air equations or saturation-vapor-pressure formulas;
- atmosphere interpolation, caching policy, or table format;
- wind-direction convenience conversions;
- gravity or a gravity-field provider;
- reference-frame angular velocity;
- Coriolis, centrifugal, Euler, transport-rate, or Eötvös calculations;
- relative-air velocity;
- Mach number;
- dynamic pressure;
- aerodynamic coefficients;
- drag, lift, Magnus, spin damping, yaw-of-repose, or aerodynamic moments;

## 27. EB0.1-B6 reference-frame sample

EB0.1-B6 defines one already-sampled local reference-frame/gravity value. It
freezes the physical meaning, coordinate-frame meaning, precision families,
public member order, and validation of the quantities that later
non-inertial-acceleration code will consume.

Like the B4 environment sample, the B6 value record deliberately does not define
how the sample is obtained. A later provider checkpoint may evaluate constant
gravity/frame kinematics, an analytic planetary model, a table, a navigation
solution, a Cubes of Honor world model, or another caller-owned source.

### 27.1 Public header and precision-qualified sample types

EB0.1-B6 introduces:

```text
include/bbtc/external_ballistics/reference_frame.h
```

The external-ballistics umbrella header MUST include this public header once B6
is implemented.

The public sample types are:

```c
bbtc_eb_reference_frame_sample_float_t
bbtc_eb_reference_frame_sample_double_t
bbtc_eb_reference_frame_sample_long_double_t
```

Each sample contains the following members in this exact declaration order:

```text
gravitational_acceleration_reference_m_per_s2
reference_frame_origin_acceleration_reference_m_per_s2
reference_frame_angular_velocity_reference_rad_per_s
reference_frame_angular_acceleration_reference_rad_per_s2
```

Every member is the matching native precision-qualified BBTC three-vector type.

All four members therefore have identical structural type size within one
precision family. The declaration order above is a public semantic contract;
EB0.1-B6 does not claim that the order provides a universal padding or ABI-size
optimization.

### 27.2 Gravitational acceleration

`gravitational_acceleration_reference_m_per_s2` is the physical
gravitational-field acceleration at the projectile sample point, expressed in
the active BBTC reference frame.

It MUST NOT contain:

- Coriolis acceleration;
- centrifugal acceleration;
- Euler acceleration;
- acceleration caused solely by translation of the active reference-frame
  origin;
- aerodynamic acceleration;
- contact or support acceleration;
- propulsion; or
- another separately modeled force/acceleration contribution.

The vector may have any finite magnitude and direction, including exactly zero.
The generic B6 validator does not impose an Earth gravity magnitude, a fixed
down axis, an inverse-square law, a planetary center, or a standard-gravity
constant.

### 27.3 Reference-frame origin acceleration

`reference_frame_origin_acceleration_reference_m_per_s2` is the inertial
translational acceleration of the origin of the active BBTC reference frame,
expressed in the active reference-frame axes.

This is a kinematic quantity. It does not mean "gravity at the origin" and BBTC
does not infer its physical cause.

For a stationary inertial frame, this vector is exactly zero.

The stored vector MUST represent the complete inertial translational
acceleration of the active reference-frame origin required by the selected
frame model. It MUST NOT omit a known contribution merely because that
contribution is rotational, planetary, vehicle-induced, or otherwise modeled
outside the projectile state.

For an ideal Earth-fixed local frame whose origin rigidly co-rotates with the
planet, this quantity therefore includes the inertial centripetal acceleration
of that local origin caused by planetary rotation. Earth-specific geometry
needed to obtain that acceleration remains outside the generic B6 sample. This
permits the projectile's `position_m` to remain local or muzzle-relative
instead of being reinterpreted as an Earth-centered vector.

### 27.4 Reference-frame angular velocity

`reference_frame_angular_velocity_reference_rad_per_s` is the angular velocity
of the active BBTC reference frame **relative to an inertial frame**, expressed
in the active reference-frame axes, in radians per second.

It is the total angular velocity needed by the generic rotating-frame
kinematics. If a specialized navigation or planetary model decomposes frame
rotation into Earth/planet rotation, transport rate, local-frame curvature, or
other components, those components MUST be combined consistently before the
generic rotating-frame evaluation unless a later reviewed API explicitly
defines a different decomposition.

A zero vector denotes no instantaneous frame rotation relative to inertial
space.

### 27.5 Reference-frame angular acceleration

`reference_frame_angular_acceleration_reference_rad_per_s2` is the time
derivative, taken with respect to the inertial frame, of the active reference
frame's angular-velocity vector relative to that inertial frame. The resulting
angular-acceleration vector is expressed in active reference-frame axes, in
radians per second squared.

This quantity supplies the future Euler-acceleration term. It may be zero even
when angular velocity is nonzero, as for an ideal uniformly rotating frame, and
it may be nonzero when angular velocity is instantaneously zero.

The generic validator imposes no cross-field consistency relation between
angular velocity and angular acceleration.

### 27.6 Zero sample and inertial-frame semantics

Unlike the B4 environment sample, the all-zero B6 reference-frame sample is
valid.

The exact zero sample denotes, at the sampled event:

- zero gravitational acceleration;
- zero inertial acceleration of the active reference-frame origin;
- zero active-frame angular velocity relative to inertial space; and
- zero active-frame angular acceleration.

It therefore represents an inertial, nonaccelerating, nonrotating,
zero-gravity reference-frame condition suitable for vacuum/free-motion
validation.

Negative zero is not assigned distinct physical meaning.

### 27.7 Validation and deterministic precedence

EB0.1-B6 exposes:

```c
bbtc_eb_reference_frame_sample_validate_float
bbtc_eb_reference_frame_sample_validate_double
bbtc_eb_reference_frame_sample_validate_long_double
```

Each validator is read-only and MUST use this exact precedence:

1. a null sample pointer returns `BBTC_STATUS_INVALID_ARGUMENT`;
2. otherwise, if any component of any member vector is NaN, return
   `BBTC_STATUS_NAN_INPUT`;
3. otherwise, if any component of any member vector is positive or negative
   infinity, return `BBTC_STATUS_NONFINITE_INPUT`;
4. otherwise return `BBTC_STATUS_SUCCESS`.

The validator MUST scan the complete record for NaN before performing the
complete infinity scan so member declaration order cannot change diagnostic
precedence.

EB0.1-B6 defines no additional magnitude, sign, direction, normalization,
planetary, or cross-field domain restriction. Validation MUST NOT:

- clamp or repair any vector;
- replace negative zero;
- normalize angular quantities;
- derive origin acceleration from angular velocity;
- derive gravity from origin acceleration;
- derive angular acceleration from angular velocity history;
- add or remove centrifugal acceleration; or
- infer Earth-specific values.

### 27.8 Ownership, layout, and precision

B6 samples are plain caller-owned values with no pointers, callbacks, dynamic
storage, allocators, reference counts, host handles, or Cubes of Honor types.

Each precision family stores and validates entirely in its native scalar family.
No public operation may route float or long-double samples through double as an
implementation shortcut.

Natural ISO C object layout applies. EB0.1-B6 freezes named member order and
native member types but does not freeze one universal `sizeof`, alignment,
padding pattern, byte serialization, or foreign-language binary layout.

Consumers MUST use named members rather than type-punning the record.

### 27.9 Relationship to future rotating-frame evaluation

EB0.1-B6 stores the input quantities needed by a future non-inertial
translational-acceleration evaluator but does not perform that evaluation.

A later reviewed evaluator will consume projectile reference-frame position and
velocity together with a B6 sample and apply the sign convention frozen in
section 11:

```text
-a_origin_R
-2 * omega_R x v_R
-alpha_R x r_R
```

## 29. EB0.1-B7 reference-frame provider interface

EB0.1-B7 establishes the caller-controlled mechanism that obtains the B6
reference-frame sample at an arbitrary projectile center-of-mass position and
simulation time.

The provider boundary mirrors the architectural role of the EB0.1-B5
environment provider while remaining a distinct public interface. A provider
may represent constant gravity and frame kinematics, an analytic planetary
model, a table, an externally maintained navigation/reference-frame solution, a
Cubes of Honor world model, or another caller-owned source.

The generic BBTC provider layer does not implement Earth geometry, gravity
models, Coriolis acceleration, centrifugal acceleration, Euler acceleration,
Eötvös behavior, or numerical integration. It only validates a sampling
request, dispatches the callback, and revalidates the returned B6 value.

### 29.1 Sampling inputs

A B7 reference-frame-provider request is defined by:

- projectile center-of-mass position in metres, measured from the active BBTC
  reference-frame origin and expressed in active-reference coordinates; and
- simulation time in seconds measured from the external-ballistics initial
  state.

For the currently frozen rigid-body state contract, the position input has the
same physical meaning as the translational `position_m` state vector.

Position components MUST be finite. Sampling time MUST be finite and greater
than or equal to zero.

The provider callback MUST NOT require projectile velocity merely to evaluate
the B6 value. Velocity-dependent non-inertial effects such as Coriolis
acceleration belong to the later non-inertial-acceleration evaluator, which
will consume projectile velocity separately.

Likewise, the B7 callback MUST NOT require projectile orientation, body angular
velocity, mass, inertia, aerodynamic coefficients, atmosphere values, force or
moment accumulators, collision state, rendering state, or gameplay state merely
to obtain one B6 sample.

A caller-owned context may refer to configuration or to an externally managed
deterministic frame-model snapshot. Such context does not change the explicit
meaning of the provider inputs and MUST NOT make callback results depend on the
result of a previous provider invocation.

A future specialized architecture for a trajectory-following coordinate frame
whose own kinematics are dynamically coupled to projectile velocity or other
projectile state is outside EB0.1-B7. Such a model MUST NOT be smuggled into
this provider through hidden call-order dependence.

### 29.2 Public header and precision-qualified callback types

EB0.1-B7 introduces:

```text
include/bbtc/external_ballistics/reference_frame_provider.h
```

The external-ballistics umbrella header MUST include this public header once B7
is implemented.

The precision-qualified callback types are:

```c
bbtc_eb_reference_frame_provider_float_fn
bbtc_eb_reference_frame_provider_double_fn
bbtc_eb_reference_frame_provider_long_double_fn
```

Conceptually, each callback has the native-family form:

```c
bbtc_status_e callback(
    const void* context,
    const bbtc_eb_vec3_*_t* position_reference_m,
    SCALAR time_s,
    bbtc_eb_reference_frame_sample_*_t* out_sample
);
```

The exact callback parameter order above is frozen by EB0.1-B7.

`position_reference_m` is the projectile center-of-mass position measured from
the active reference-frame origin and expressed in active-reference axes.

`time_s` is simulation time measured from the external-ballistics initial state.

`out_sample` is caller-owned storage for one complete B6 reference-frame
sample.

The matching provider descriptor types are:

```c
bbtc_eb_reference_frame_provider_float_t
bbtc_eb_reference_frame_provider_double_t
bbtc_eb_reference_frame_provider_long_double_t
```

Each descriptor contains the following fields in this exact declaration order:

```text
sample
context
```

`sample` is the matching precision-qualified callback pointer.

`context` is a borrowed `const void*` supplied unchanged to the callback. A
null context pointer is valid. BBTC does not allocate, free, retain, clone,
mutate, or interpret the pointed-to storage.

No public alignment override is introduced.

### 29.3 Provider dispatch functions

BBTC exposes the following precision-qualified dispatch functions:

```c

bbtc_eb_reference_frame_provider_sample_double
bbtc_eb_reference_frame_provider_sample_long_double
```

Conceptually, each function has the native-family form:

```c

    const bbtc_eb_reference_frame_provider_*_t* provider,
    const bbtc_eb_vec3_*_t* position_reference_m,
    SCALAR time_s,
    bbtc_eb_reference_frame_sample_*_t* out_sample
);
```

The dispatch layer owns common request validation and successful B6 sample
revalidation so future derivative or solver code does not duplicate provider
boundary rules.

### 29.4 Callback contract

A provider callback returning `BBTC_STATUS_SUCCESS` MUST have fully initialized
every named field of `out_sample` with one complete B6 reference-frame sample.

The callback output MUST obey all B6 semantic rules. In particular:

- the gravitational-acceleration member contains physical gravitational-field
  acceleration rather than effective/apparent gravity with non-inertial terms
  already added;
- the origin-acceleration member contains the complete inertial translational
  acceleration of the active reference-frame origin required by the selected
  frame model;
- angular velocity is the active frame's total angular velocity relative to
  inertial space, expressed in active-reference axes; and
- angular acceleration has the B6 meaning required by the future Euler term.

Dispatch MUST revalidate callback success through the matching B6 validator.
Validation does not prove that a physically mislabeled effective-gravity value
has the correct semantics; the provider implementation remains responsible for
the physical meaning of finite values.

A callback returning any non-success BBTC status communicates sampling failure.
Dispatch MUST propagate that status unchanged after restoring the deterministic
failure output described in section 29.5.

Callbacks MUST tolerate repeated requests, intermediate numerical-stage
requests, and deliberately out-of-order positions or times. They MUST NOT
assume one call per integration step, one call per render frame, or monotonically
increasing time.

Within one deterministic simulation snapshot, provider behavior MUST be a
function of explicit position, explicit time, and context rather than mutable
sampling history. Internal caching MAY be used only when it is observationally
equivalent to that rule.

BBTC does not serialize callbacks. If context refers to mutable or shared data,
the caller/provider owns synchronization and deterministic snapshot semantics.

### 29.5 Dispatch validation, deterministic output, and precedence

`out_sample` is a required caller-owned output pointer.

If `out_sample` is null, dispatch MUST return `BBTC_STATUS_INVALID_ARGUMENT`.
No output-state guarantee is possible because no output object exists.

When `out_sample` is non-null, dispatch MUST write the exact all-zero B6 sample
to `*out_sample` before validating any remaining request input or invoking the
callback.

For every subsequent dispatch failure, including invalid request data, callback
failure, or invalid callback output, `*out_sample` MUST contain the exact
all-zero B6 sample on return.

Unlike the B4 environment-provider failure state, the all-zero B6 sample is
itself a valid physical B6 value representing inertial, nonaccelerating,
nonrotating, zero-gravity conditions. Therefore **the returned status is the
authoritative indicator of provider-dispatch success or failure**. Callers MUST
NOT infer dispatch success by validating or inspecting `out_sample` alone after
a non-success return.

This zero-on-failure rule is a deterministic storage policy, not an invalid
sentinel convention.

Dispatch MUST use this exact validation and failure order:

1. a null output pointer returns `BBTC_STATUS_INVALID_ARGUMENT`;
2. otherwise dispatch first establishes the all-zero B6 output state;
3. null provider, null provider callback, or null position pointer returns
   `BBTC_STATUS_INVALID_ARGUMENT`;
4. otherwise, if any position component or `time_s` is NaN, return
   `BBTC_STATUS_NAN_INPUT`;
5. otherwise, if any position component or `time_s` is infinite, return
   `BBTC_STATUS_NONFINITE_INPUT`;
6. otherwise, if `time_s` is negative, return `BBTC_STATUS_OUTSIDE_DOMAIN`;
7. otherwise invoke the provider callback exactly once;
8. if the callback returns a non-success status, restore the all-zero B6 sample
   and return that status unchanged;
9. otherwise validate the callback-produced sample with the matching B6
   validator;
10. if B6 validation fails, restore the all-zero B6 sample and return the B6
    validator status; and
11. otherwise return `BBTC_STATUS_SUCCESS` and preserve the validated callback
    output.

The callback MUST NOT be invoked when dispatch rejects the request before step
7.

The precedence above intentionally makes null-pointer diagnostics dominate
numeric request diagnostics and makes NaN dominate infinity across the complete
request vector/time set.

### 29.6 Precision and ABI rules

Each provider family operates entirely in its native scalar family:

- float position, time, callback, provider descriptor, and B6 sample;
- double position, time, callback, provider descriptor, and B6 sample; and
- long-double position, time, callback, provider descriptor, and B6 sample.

Dispatch MUST NOT convert through another precision family.

Provider descriptors are plain borrowed-interface values. They contain no
owned allocation, reference count, BBTC-owned host handle, Cubes of Honor type,
or hidden lifetime management.

Function-pointer representation, object-pointer representation, padding,
alignment, and universal byte size remain implementation properties. EB0.1-B7
freezes only the named member order and C type identities explicitly stated by
this contract.

### 29.7 Earth-like and host-provider responsibilities

An Earth-specific provider MAY use latitude, longitude, ellipsoid geometry,
planetary radius, Earth rotation, time, gravity models, or another physically
reviewed model to construct the B6 sample.

Such a provider MUST preserve the B6 separation between gravitational-field
acceleration and non-inertial frame kinematics. It MUST NOT hide centrifugal,
Coriolis, Euler, or duplicate Eötvös acceleration inside the gravitational
member merely because an external source labels the combined value "gravity".

Cubes of Honor MAY implement a B7 provider whose context refers to
caller-owned world/reference-frame state. The adapter may convert BBTC
reference coordinates and simulation time into whatever world queries are
required, then convert the resulting quantities into one B6 sample.

BBTC MUST NOT include Cubes of Honor headers or assume a particular host
context representation.

### 29.8 Relationship to future non-inertial acceleration

B7 provides the B6 inputs required by a later reviewed non-inertial
translational-acceleration evaluator. B7 itself MUST NOT evaluate:

```text

-2 * omega_R x v_R
-alpha_R x r_R
-omega_R x (omega_R x r_R)
```

In particular, projectile velocity is deliberately absent from the B7 provider
callback because Coriolis acceleration is a consumer-side result of combining
projectile velocity with the sampled frame angular velocity.

For applicable Earth models, later Eötvös validation remains mandatory and must
arise from the complete frame formulation without a separately duplicated

## 31. EB0.1-B8 applied force and moment value boundary

EB0.1-B8 establishes the first public external-ballistics value record for
resultant applied mechanical force and applied moment.

The checkpoint is intentionally representation-focused. It defines frames,
units, physical inclusion/exclusion rules, native precision families, and
validation behavior before a later equations-of-motion checkpoint consumes the
values.

EB0.1-B8 does NOT evaluate forces or moments, sample an aerodynamic model,
perform rigid-body derivative evaluation, or integrate state.

### 31.1 Physical role and separation from acceleration inputs

The B8 force/moment record represents physical applied mechanical loading that
is intended to enter later rigid-body equations of motion.

For translational dynamics, B8 applied force is deliberately separate from
accelerations already represented by the B6 reference-frame sample.

In particular, the B8 applied-force member MUST NOT contain a force-equivalent
duplicate of:

- the B6 physical gravitational-field acceleration;
- reference-frame-origin translational acceleration;
- Coriolis acceleration;
- Euler acceleration; or
- centrifugal acceleration.

A future equations-of-motion evaluator is expected to combine applied force
through `F / m` with gravitational and, where applicable, non-inertial
acceleration terms exactly once.

This separation prevents a caller from supplying `m * g` as B8 force while
also supplying the same gravitational field through B6.

Physical forces not otherwise represented by another BBTC acceleration
contract MAY be reduced into B8 applied force. Future examples may include
aerodynamic, propulsion, electromagnetic, or other explicitly modeled physical
forces, provided they are not duplicated elsewhere.

The B8 moment member represents physical applied moment about the projectile
center of mass. A future model that independently computes a physical torque
such as aerodynamic or gravity-gradient moment MAY represent that torque in
B8 when it is not otherwise modeled elsewhere.

The B8 applied-moment member MUST contain physical applied torque only. It MUST
NOT contain a fictitious or kinematic correction moment introduced solely by
expressing rotational motion in an accelerating or rotating reference frame.
Any such non-inertial rotational terms belong to a later reviewed
equations-of-motion/reference-frame checkpoint and MUST NOT be double counted
through B8.

EB0.1-B8 itself introduces no gravity-gradient model, aerodynamic model,
propulsion model, or contact model.

### 31.2 Frames, reference point, and units

All B8 forces and moments use SI units.

The applied-force vector is expressed in the active BBTC reference frame used by
the rigid-body state's translational position and translational velocity.

The applied-moment vector is expressed in the canonical BBTC projectile body
frame and is taken about the projectile center of mass.

This mixed-frame representation is deliberate:

- translational acceleration is evolved in active-reference axes; and
- rotational dynamics consume the body-frame angular velocity and the
  body-principal inertia representation frozen by B3.

A model that naturally computes force in body axes MUST rotate that force into
active-reference axes before storing it in B8.

A model that naturally computes moment in reference axes MUST rotate that
moment into body axes before storing it in B8.

For the frozen world/reference-from-body unit orientation quaternion `q_WB`,
body-to-reference conversion follows the active Hamilton convention already
frozen by sections 5.1 and 7. Reference-to-body conversion is the corresponding
inverse/conjugate rotation.

The B8 record does not contain a force application point. Any distributed load
or off-center force model that contributes to B8 is responsible for reducing
its effect to:

- one resultant applied force; and
- one resultant applied moment about the center of mass.

### 31.4 Contribution and accumulation semantics

A B8 record may represent either:

- one independently computed physical contribution; or
- the algebraic resultant of multiple compatible contributions.

Independent B8 contributions combine component-wise only after each force is
expressed in active-reference axes and each moment is expressed in body axes
about the center of mass.

Mathematically, the resultant is the vector sum of the participating force
vectors and the vector sum of the participating moment vectors.

EB0.1-B8 does not expose a public accumulator API and does not freeze one
floating-point accumulation order. A later force-model architecture may define
an explicit accumulation strategy if deterministic ordering, compensated
summation, or another numerical policy becomes necessary.

No contribution may be added twice under different names. In particular,
gravity and reference-frame kinematic accelerations remain outside B8 applied
force as stated in section 31.1.

### 31.5 Validation API

EB0.1-B8 introduces:

```c

bbtc_eb_force_moment_validate_long_double
```

Conceptually, each validator has the native-family form:

```c

    const bbtc_eb_force_moment_*_t* force_moment

```

Validation is read-only. Validators MUST NOT rotate, normalize, clamp, derive,
accumulate, repair, or otherwise modify the caller-owned record.

Validation MUST use this exact precedence:

1. a null pointer returns `BBTC_STATUS_INVALID_ARGUMENT`;
2. otherwise, if any component of either vector is NaN, return
   `BBTC_STATUS_NAN_INPUT`;
3. otherwise, if any component of either vector is positive or negative
   infinity, return `BBTC_STATUS_NONFINITE_INPUT`; and
4. otherwise return `BBTC_STATUS_SUCCESS`.

The validator MUST perform a complete NaN scan across all six stored scalar
components before deciding whether any infinity is present.

No magnitude, sign, direction, orthogonality, symmetry, mass, inertia,
reference-area, or relationship constraint is imposed by B8 validation.

Arbitrary finite positive, negative, and zero force/moment components are valid.

### 31.7 Relationship to future equations of motion

For rotation, the future evaluator is expected to combine the B8 body-frame
applied moment with body-frame angular velocity and principal moments of inertia
through the rigid-body Euler equation.

EB0.1-B8 freezes these architectural roles but does not yet implement the
equations.

## 33. EB0.1-B9 rigid-body state-derivative value boundary

EB0.1-B9 establishes the public value representation for the derivative of the
integrated external-ballistics rigid-body dependent variables.

This checkpoint freezes representation, units, frame semantics, native scalar
families, and validation behavior only. It does not define the physical
equations that produce a derivative and does not numerically advance state.

The high-level implementation sequence in section 15 reserves vacuum
six-degree-of-freedom propagation and analytic validation for EB1. B9 therefore
provides an integration-facing derivative value without prematurely moving EB1
equations of motion into EB0.

### 33.1 Dependent variables and independent time

The B1 rigid-body state contains projectile orientation, position,
translational velocity, body-frame angular velocity, and simulation time.

For numerical integration, simulation time is the independent variable. The B9
derivative record therefore represents derivatives of the four physical
dependent-variable groups:

- world/reference-from-body orientation;
- reference-frame position;
- reference-frame translational velocity; and
- body-frame angular velocity.

B9 intentionally contains no `time_derivative` member.

A future integrator MUST advance the state's `time_s` explicitly from the
requested time step and MUST assign the appropriate stage time to intermediate
states before invoking a derivative evaluator. It MUST NOT require a stored
`dt/dt` value merely to advance time.

For ordinary integration, the mathematical identity `dt/dt = 1` is implicit in
the integrator's treatment of time as the independent variable rather than a
caller-supplied derivative component.

### 33.2 Public header and precision-qualified derivative records

EB0.1-B9 introduces:

```text
include/bbtc/external_ballistics/state_derivative.h
```

The external-ballistics umbrella header MUST include this public header once B9
is implemented.

The precision-qualified derivative records are:

```c
bbtc_eb_rigid_body_state_derivative_float_t
bbtc_eb_rigid_body_state_derivative_double_t
bbtc_eb_rigid_body_state_derivative_long_double_t
```

Each record contains the following members in this exact declaration order:

```text
orientation_world_from_body_derivative_per_s
position_derivative_reference_m_per_s
velocity_derivative_reference_m_per_s2
angular_velocity_derivative_body_rad_per_s2
```

The orientation-derivative member uses the matching native BBTC quaternion
record. Each remaining member uses the matching native BBTC three-dimensional
vector record.

No public alignment override is introduced.

### 33.3 Orientation-derivative semantics

`orientation_world_from_body_derivative_per_s` is the component-wise time
derivative of the frozen active world/reference-from-body orientation
quaternion. Its four components have reciprocal-second semantics because the
orientation quaternion itself is dimensionless.

A quaternion derivative is NOT an orientation quaternion.

Accordingly:

- it is not required to have unit norm;
- it is not required to have nonzero norm;
- it MUST NOT be normalized merely to make it look like an orientation; and
- the exact all-zero quaternion derivative is valid derivative storage.

Section 12 already freezes the future physical orientation-kinematics relation

```text
dq_WB/dt = 0.5 * q_WB * omega_B_quat
```

for the world/reference-from-body orientation and body-frame angular velocity.
B9 preserves a value capable of storing that result but does NOT evaluate the
equation.

The legacy pre-rewrite multiplication-order discrepancy recorded in section
19.1 remains a required EB1 test concern and is not resolved merely by storing
a B9 derivative value.

### 33.4 Translational derivative semantics

`position_derivative_reference_m_per_s` is the time derivative of projectile
center-of-mass position, expressed in active-reference axes, in metres per
second.

For a physically evaluated rigid-body state derivative, section 12 requires
this quantity to equal the projectile translational velocity in the active
reference frame.

B9 validation does NOT enforce that relationship because the derivative record
does not contain the state from which it was derived. The equality belongs to a
future equations-of-motion evaluator and its tests.

`velocity_derivative_reference_m_per_s2` is the time derivative of
translational velocity, expressed in active-reference axes, in metres per
second squared.

The B9 value contract does not prescribe which physical contributions are
present in that acceleration. A later reviewed equations-of-motion checkpoint
will define how B8 applied force, projectile mass, gravity, and later
reference-frame effects enter it.

### 33.5 Angular-velocity derivative semantics

`angular_velocity_derivative_body_rad_per_s2` is the time derivative of the
projectile angular-velocity components stored by the rigid-body state,
expressed in the canonical BBTC projectile body frame, in radians per second
squared.

B9 does not compute this value.

A later EB1 equations-of-motion implementation is expected to derive it from
body-frame applied moment, body-frame angular velocity, and the B3 principal
moments of inertia through the reviewed rigid-body Euler equations.

The B9 validator does not require any relationship between the angular-velocity
derivative and projectile inertia, applied moment, orientation, or any other
record.

### 33.6 Zero and arbitrary finite derivative values

The exact all-zero B9 derivative record is valid.

It represents a mathematically representable instantaneous zero derivative of
all four dependent-variable groups. B9 validation does not decide whether such
a derivative is physically consistent with a separately supplied state or
loading condition.

Arbitrary finite positive, negative, and zero components are valid in every
member.

B9 validation imposes no:

- quaternion norm requirement;
- direction or magnitude restriction;
- equality between position derivative and any external state velocity;
- relationship between velocity derivative and force, mass, or gravity;
- relationship between angular-velocity derivative and moment or inertia; or
- cross-member physical consistency rule.

Those are equations-of-motion concerns rather than value-representation
concerns.

### 33.7 Validation API and deterministic precedence

EB0.1-B9 introduces:

```c
bbtc_eb_rigid_body_state_derivative_validate_float
bbtc_eb_rigid_body_state_derivative_validate_double
bbtc_eb_rigid_body_state_derivative_validate_long_double
```

Conceptually, each validator has the native-family form:

```c
bbtc_status_e bbtc_eb_rigid_body_state_derivative_validate_*(
    const bbtc_eb_rigid_body_state_derivative_*_t* derivative
);
```

Validation is read-only. A validator MUST NOT normalize, rotate, clamp, derive,
repair, or otherwise modify caller-owned storage.

The derivative contains thirteen scalar components:

- four orientation-derivative components;
- three position-derivative components;
- three velocity-derivative components; and
- three angular-velocity-derivative components.

Validation MUST use this exact precedence:

1. a null pointer returns `BBTC_STATUS_INVALID_ARGUMENT`;
2. otherwise, if any of the thirteen scalar components is NaN, return
   `BBTC_STATUS_NAN_INPUT`;
3. otherwise, if any component is positive or negative infinity, return
   `BBTC_STATUS_NONFINITE_INPUT`; and
4. otherwise return `BBTC_STATUS_SUCCESS`.

The validator MUST perform a complete NaN scan across all thirteen stored
scalars before deciding whether any infinity is present.

No additional domain failure is defined by B9.

### 33.8 Precision and ABI rules

Each B9 family operates entirely in its native scalar family:

- float derivative members and validation remain native `float`;
- double derivative members and validation remain native `double`; and
- long-double derivative members and validation remain native `long double`.

Validation MUST NOT convert through another precision family.

EB0.1-B9 freezes only:

- the three derivative record type names;
- the four member names;
- their exact declaration order;
- their native quaternion/vector type identities;
- their units and frame meanings;
- the absence of a stored time-derivative member; and
- the three validator names and validation semantics.

Padding, byte size, alignment, and other implementation-specific ABI details
remain implementation properties.

### 33.9 Relationship to future derivative evaluation and integration

numerical integration.

Conceptually:

```text

                  |
```

## 35. EB0.1-B10 rigid-body state-derivative provider boundary

EB0.1-B10 establishes the generic callback/provider boundary through which a
future numerical integrator requests one B9 rigid-body state derivative for one
candidate B1 rigid-body state.

The provider boundary deliberately knows nothing about the physical origin of
the derivative. A callback may later represent vacuum rigid-body equations,
aerodynamic equations, a test oracle, or another reviewed model while exposing
the same state-to-derivative interface to an integrator.

B10 freezes callback signatures, provider descriptors, dispatch semantics,
input/output validation, ownership, and deterministic failure behavior only.

It does NOT implement the physical equations that produce a derivative and does
NOT advance state numerically.

### 35.1 Public header and callback families

EB0.1-B10 introduces:

```text
include/bbtc/external_ballistics/state_derivative_provider.h
```

The public callback types are:

```c
bbtc_eb_state_derivative_provider_float_fn
bbtc_eb_state_derivative_provider_double_fn
bbtc_eb_state_derivative_provider_long_double_fn
```

Conceptually, each native-family callback has the form:

```c
bbtc_status_e callback(
    const void* context,
    const bbtc_eb_rigid_body_state_*_t* state,
    bbtc_eb_rigid_body_state_derivative_*_t* out_derivative
);
```

The scalar/vector/quaternion family of `state` and `out_derivative` MUST match
the callback precision family exactly.

The callback receives the complete B1 rigid-body state. In particular,
`state->time_s` is the authoritative simulation/stage time.

B10 intentionally provides NO separate callback time argument. A duplicated
time scalar could disagree with `state->time_s` and would weaken the invariant
that one callback request represents one complete candidate state at one
specific integration time.

A future integrator MUST therefore assign the intended stage time to an
intermediate state's `time_s` before requesting its derivative.

### 35.2 Provider descriptors

The public provider descriptor types are:

```c
bbtc_eb_state_derivative_provider_float_t
bbtc_eb_state_derivative_provider_double_t
bbtc_eb_state_derivative_provider_long_double_t
```

Each descriptor contains the following members in this exact declaration order:

```text
evaluate
context
```

`evaluate` is the matching native callback type.

`context` has type:

```c
const void*
```

and is borrowed caller-owned provider context. It MAY be null; a null context
pointer alone does not make a provider invalid. BBTC neither allocates nor frees
it.

The context may refer to immutable configuration, caller-managed snapshots, or
other data required by a concrete derivative evaluator. The generic B10
dispatcher does not interpret the pointed-to object.

No public alignment override is introduced.

### 35.3 Callback request semantics

A derivative request represents:

```text
(state, context) -> derivative
```

The state pointer supplied to the callback is borrowed and read-only for the
duration of the call. The callback MUST NOT modify the state object and MUST NOT
retain the state pointer after returning.

The output pointer is writable callback output storage owned by the caller.

The provider context pointer is borrowed according to the lifetime established
by the caller. B10 does not copy, clone, serialize, or otherwise manage provider
context.

A callback MAY use immutable or externally synchronized context. If context
contains mutable/shared state, the provider/caller owns the synchronization and
snapshot-consistency policy. BBTC does not serialize provider callbacks.

### 35.4 Repeated, intermediate, and out-of-order evaluation

A derivative provider MUST support requests generated by numerical integration
algorithms rather than assuming one monotonically advancing sequence of final
simulation states.

In particular, callbacks MUST tolerate:

- repeated evaluation of the same state and time;
- multiple distinct states with the same `time_s`;
- intermediate stage states;
- retries after an integration attempt; and
- requests whose times are not monotonically increasing relative to prior
  invocations.

The physical result for one request MUST NOT depend on hidden mutation caused
merely by the order of previous B10 callback invocations.

A concrete provider MAY consult caller-managed external state through its
context, but call history internal to the provider MUST NOT silently become an
additional independent physical input.

This requirement preserves the ability to use fixed-step Runge-Kutta,
adaptive methods, test oracles, and future integration algorithms through the
same provider boundary.

### 35.5 Callback-visible state validity

The generic B10 dispatch boundary accepts only a rigid-body state that satisfies
the matching B2 public state validator.

Therefore every callback-visible candidate state has already passed the frozen
state requirements, including:

- finite orientation, position, velocity, angular velocity, and time;
- nonnegative simulation time; and
- a nonzero orientation sufficiently close to unit length under the B2
  tolerance.

B10 itself does NOT define how a future integrator constructs such intermediate
states or controls quaternion drift.

A future numerical integrator MUST document and test its quaternion
constraint-control strategy and MUST ensure any state presented to a B10
provider satisfies the public rigid-body-state contract.

That future strategy MAY normalize internally generated intermediate or final
orientations to control ordinary integration drift, as allowed by section 12,
but it MUST NOT use normalization to silently accept an invalid initial public
state supplied by the caller.

### 35.6 Dispatch API

EB0.1-B10 introduces:

```c
bbtc_eb_state_derivative_provider_evaluate_float
bbtc_eb_state_derivative_provider_evaluate_double
bbtc_eb_state_derivative_provider_evaluate_long_double
```

Conceptually, each native-family dispatch function has the form:

```c
bbtc_status_e bbtc_eb_state_derivative_provider_evaluate_*(
    const bbtc_eb_state_derivative_provider_*_t* provider,
    const bbtc_eb_rigid_body_state_*_t* state,
    bbtc_eb_rigid_body_state_derivative_*_t* out_derivative
);
```

Dispatch remains entirely within the matching native precision family.

### 35.7 Deterministic dispatch failure semantics

Each dispatch function MUST use this exact precedence:

1. if `out_derivative` is null, return `BBTC_STATUS_INVALID_ARGUMENT`;
2. otherwise clear `*out_derivative` to the exact all-zero B9 derivative;
3. if `provider`, `provider->evaluate`, or `state` is null, return
   `BBTC_STATUS_INVALID_ARGUMENT`;
4. validate `state` with the matching B2 rigid-body-state validator;
5. if state validation fails, return that status unchanged while preserving the
   zeroed output;
6. invoke `provider->evaluate` exactly once;
7. if the callback returns a non-success status, clear the output again and
   propagate the callback status unchanged;
8. if the callback reports success, validate `*out_derivative` with the matching
   B9 state-derivative validator;
9. if derivative validation fails, clear the output and return that validation
   status; and
10. otherwise return `BBTC_STATUS_SUCCESS` while preserving the callback output.

No callback invocation occurs when the provider descriptor is invalid or when
the candidate state fails B2 validation.

If the callback returns a non-success status, that callback status takes
precedence over any derivative contents written by the callback. B9 derivative
validation occurs only after the callback itself reports
`BBTC_STATUS_SUCCESS`.

### 35.8 All-zero derivative and status authority

The exact all-zero B9 derivative is valid physical/mathematical derivative
data.

Therefore B10 MUST NOT use an all-zero derivative as an invalid-data sentinel.

A callback MAY validly return:

```text
BBTC_STATUS_SUCCESS
```

together with an exact all-zero derivative.

The `bbtc_status_e` result is authoritative for success/failure. Zeroing output
on failure exists only to provide deterministic fail-closed storage.

### 35.9 Callback output ownership and failure behavior

Before callback invocation, the dispatcher MUST present the callback with an
already-zeroed output derivative.

A successful callback may overwrite any or all output fields. Because the
all-zero derivative is valid, a callback is not required to write nonzero data
to demonstrate success.

If the callback returns failure after writing partial or complete output, the
dispatcher MUST restore the output to the exact all-zero derivative before
returning.

If a callback reports success but produces NaN or infinity in any B9 component,
the matching B9 validator status is returned and the output is restored to
all-zero.

No partially valid derivative escapes a failed dispatch.

### 35.10 Precision, allocation, and host-independence rules

Each B10 family is native throughout:

- float provider/callback/dispatch uses only float-family B1/B9 records;
- double provider/callback/dispatch uses only double-family B1/B9 records; and
- long-double provider/callback/dispatch uses only long-double-family B1/B9
  records.

The B10 generic dispatch layer MUST NOT convert through another precision
family.

B10 requires no dynamic allocation, file I/O, process termination, global
mutable state, Cubes of Honor header, or host-engine mathematical type.

The provider boundary remains usable through the ordinary standalone
`bbtc::bbtc` library target.

## 37. EB0.1-B11 fixed-step RK4 integration boundary

EB0.1-B11 establishes the first public numerical-integration operation for the
external-ballistics rigid-body state and completes the EB0 integration
architecture.

B11 consumes the B10 rigid-body state-derivative provider boundary and advances
one B1 rigid-body state through one positive fixed time step using a
correctness-oriented classical fourth-order Runge-Kutta construction for the
stored dependent-variable components.

Quaternion orientation requires an explicit constraint-control policy because
B10 accepts only callback-visible states satisfying the B2 orientation
contract. B11 therefore uses RK4 with quaternion projection by normalization on
internally generated stage orientations and on the final orientation.

B11 remains completely agnostic to the physical equations that produce the B9
derivative. It does NOT implement vacuum or aerodynamic equations of motion.

### 37.1 Public header and step API

EB0.1-B11 introduces:

```text
include/bbtc/external_ballistics/integrator.h
```

and the public native-family functions:

```c
bbtc_eb_rk4_step_float
bbtc_eb_rk4_step_double
bbtc_eb_rk4_step_long_double
```

Conceptually, each has the form:

```c
bbtc_status_e bbtc_eb_rk4_step_*(
    const bbtc_eb_state_derivative_provider_*_t* provider,
    SCALAR step_s,
    bbtc_eb_rigid_body_state_*_t* state
);
```

`state` is an in/out object.

On success, it is replaced with the advanced state at
`old_state.time_s + step_s`.

On failure, the caller-owned state object MUST remain bit-for-bit unchanged.

This transactional in-place design intentionally avoids a public input/output
aliasing problem and makes a failed integration attempt safe to inspect, retry,
or report.

Before the first provider dispatch, B11 MUST copy the complete caller-owned
state into local/internal storage. Every callback-visible state, including the
K1 state, MUST be supplied from local/internal storage rather than by passing
the caller's `state` pointer directly. The K1 snapshot preserves the exact
field values of the validated entry state.

Provider context and any external side effects performed by provider callbacks
are outside this transactional guarantee. For B11 use, provider context MUST
NOT be used as a writable alias to the caller-owned state being stepped, and a
callback MUST NOT mutate that state through any other alias. Such external
aliasing would violate the B11 provider-use contract because BBTC cannot roll
back mutations performed independently through caller-owned context.

### 37.2 Fixed forward-step domain

B11 supports one finite, strictly positive forward integration step.

`step_s` is expressed in seconds and MUST satisfy:

```text
isfinite(step_s) && step_s > 0
```

Zero, negative zero, negative finite steps, positive infinity, negative
infinity, and NaN are not valid B11 step requests.

B11 introduces no backward integration, adaptive step-size selection, minimum
step-size policy, maximum step-size policy, or model-specific accuracy policy.

The caller owns the choice of physically and numerically appropriate step size.

### 37.3 Request validation and deterministic input precedence

Before any provider callback is invoked, B11 MUST establish a valid request.

The pointer/descriptor checks occur first:

1. if `state` is null, return `BBTC_STATUS_INVALID_ARGUMENT`;
2. if `provider` is null or `provider->evaluate` is null, return
   `BBTC_STATUS_INVALID_ARGUMENT`.

For the floating request values, NaN and infinity precedence is global across
the initial B1 state and `step_s`.

B11 MUST determine the matching B2 state-validation result without modifying
`state`, then apply this precedence:

1. if the initial state validation result is `BBTC_STATUS_NAN_INPUT` OR
   `step_s` is NaN, return `BBTC_STATUS_NAN_INPUT`;
2. otherwise, if the initial state validation result is
   `BBTC_STATUS_NONFINITE_INPUT` OR `step_s` is positive or negative infinity,
   return `BBTC_STATUS_NONFINITE_INPUT`;
3. otherwise, if initial-state validation failed for another reason, propagate
   that B2 status unchanged;
4. otherwise, if `step_s <= 0`, return `BBTC_STATUS_OUTSIDE_DOMAIN`;
5. otherwise the request is valid for numerical stepping.

No provider callback occurs for any invalid request.

In particular, an invalid caller-supplied orientation MUST be rejected by the
ordinary B2 state contract and MUST NOT be normalized or otherwise repaired by
B11.

### 37.4 Independent time treatment

As frozen by B9 and B10, simulation time is the independent integration
variable and is not a stored derivative component.

Let:

```text
t = initial_state.time_s
h = step_s
```

B11 stage times are:

```text
K1: t
K2: t + h/2
K3: t + h/2
K4: t + h
```

The successful final state's time is exactly the native-family result of:

```text
t + h
```

B11 MUST NOT infer stage time from a derivative record.

Before each B10 provider request, the candidate stage state's `time_s` MUST be
set to the corresponding stage time.

Because `h > 0`, the final time must be finite and must compare strictly greater
than the initial time in the active native scalar family.

If native floating-point arithmetic cannot produce a finite strictly later
`t + h`, B11 MUST return `BBTC_STATUS_NUMERICAL_FAILURE` without invoking any
provider callback and without modifying the caller state.

A half-step stage time that rounds to `t` is not by itself an error provided
the final `t + h` remains finite and strictly later than `t`.

### 37.5 Classical RK4 dependent-variable construction

Let `Y0` denote the four physical dependent-variable groups in the initial B1
state:

- orientation quaternion components;
- reference-frame position;
- reference-frame translational velocity; and
- body-frame angular velocity.

Let `F(Y, t)` denote one successful B10 provider evaluation returning a B9
derivative.

Ignoring quaternion projection for the moment, B11 uses:

```text
K1 = F(Y0,                 t)
K2 = F(Y0 + (h/2) * K1,    t + h/2)
K3 = F(Y0 + (h/2) * K2,    t + h/2)
K4 = F(Y0 + h * K3,        t + h)

Y1 = Y0 + (h/6) * (K1 + 2*K2 + 2*K3 + K4)
```

Every addition and multiplication is performed directly in the matching native
scalar family.

The K4 state MUST use the full-step construction:

```text
Y0 + h * K3
```

and MUST NOT use:

```text
Y0 + (h/2) * K3
```

The latter was a known defect in legacy pre-rewrite code and is a mandatory B11
regression-test target.

State-derivative scaling/combination required by RK4 is private integrator
arithmetic and does not become a public B9 arithmetic API.

### 37.6 Quaternion stage projection and final normalization

The orientation component of an RK4 stage is formed component-wise exactly like
the other dependent variables before constraint control.

For internally generated K2, K3, and K4 candidate states, B11 MUST normalize the
candidate world/reference-from-body quaternion before presenting that state to
the B10 provider.

The K1 callback receives the caller's initial orientation exactly as supplied,
after B2 validation; B11 MUST NOT normalize the caller's initial state before
K1.

After the weighted RK4 final orientation is formed, B11 MUST normalize that
internally generated final quaternion before committing the successful state.

Quaternion normalization MUST use the existing native-family private BBTC
normalization operation or an exactly equivalent reviewed native-family
implementation.

If an internally generated stage or final quaternion is zero, NaN, infinite, or
otherwise cannot be normalized into a valid finite unit quaternion, the step
fails with:

```text
BBTC_STATUS_NUMERICAL_FAILURE
```

The caller-owned state remains unchanged.

This projection policy is constraint control for integrator-generated
orientation drift. It MUST NOT be used to accept an invalid initial public
orientation.

### 37.7 Internal stage validity

After constructing and projecting each internally generated K2, K3, or K4
candidate state, B11 MUST ensure the complete candidate satisfies the B2 state
contract before invoking the B10 provider.

If an internally generated candidate fails B2 validation, B11 MUST classify the
condition as:

```text
BBTC_STATUS_NUMERICAL_FAILURE
```

rather than exposing the generated-state validation code as though the caller
had supplied that bad state.

No provider callback is invoked for an internally generated stage that fails
this check.

The final candidate state MUST likewise satisfy B2 validation after final
orientation normalization and before it is committed to caller storage.

Any failure of that final generated-state validation is
`BBTC_STATUS_NUMERICAL_FAILURE`.

Finite underflow or ordinary rounding that still produces a B2-valid state is
not by itself a numerical failure.

### 37.8 Provider dispatch and failure propagation

Every derivative request MUST go through the matching public B10 dispatch
function.

For a successful B11 step, the provider callback is therefore invoked exactly
four times.

If K1 provider dispatch fails, B11 MUST immediately propagate that status
unchanged and perform no K2/K3/K4 request.

If K2 dispatch fails, B11 MUST propagate that status unchanged and perform no
K3/K4 request.

If K3 dispatch fails, B11 MUST propagate that status unchanged and perform no
K4 request.

If K4 dispatch fails, B11 MUST propagate that status unchanged.

In every such failure case, the caller-owned `state` remains unchanged.

B11 does not roll back or otherwise undo mutations inside caller-owned provider
context that the callback itself may have performed before returning. Such
context may contain mutable model state, diagnostics, counters, or other
caller-owned data, but during a B11 step it MUST NOT provide writable aliasing
access to the caller-owned rigid-body state being advanced.

### 37.9 Transactional state commit

B11 MUST perform all stage construction, derivative storage, quaternion
projection, and final-state construction in local/internal storage.

The caller-owned `state` MUST NOT be incrementally updated during K1-K4.

Only after:

- all four provider dispatches succeed;
- the weighted RK4 final dependent variables are constructed;
- final orientation normalization succeeds;
- final time is assigned; and
- the complete final state satisfies B2 validation

may B11 replace `*state` with the final state.

Therefore any B11 failure leaves every scalar component of the caller's state
unchanged from its entry value.

### 37.10 Native precision and arithmetic

The float B11 family operates entirely in native `float`.

The double family operates entirely in native `double`.

The long-double family operates entirely in native `long double`.

B11 MUST NOT route one family through another family for derivative scaling,
stage construction, time arithmetic, quaternion normalization, or final
combination.

Integer RK4 coefficients such as `2` and `6` are converted to the active native
scalar family as part of ordinary native arithmetic.

### 37.11 Allocation, determinism, and host independence

One B11 RK4 step requires no dynamic allocation.

It performs no file I/O, process termination, global mutable-state update,
trajectory allocation, collision query, host-engine conversion, or Cubes of
Honor operation.

For deterministic providers and identical native-family inputs, B11 itself has
no hidden history and produces deterministic stage requests and output under
the active floating-point environment.

B11 does not cache provider results across calls.

### 37.12 Synthetic numerical validation

B11 MUST be validated independently of EB1 ballistic physics.

At minimum, tests MUST include synthetic B10 providers whose mathematical
behavior is simple enough to determine the expected RK4 stages or result
directly.

A mandatory regression oracle is the scalar test equation embedded in one B1
state component:

```text
dx/dt = x
x(0) = 1
h = 1
```

using, for example, one position component while all unrelated derivative
components remain zero.

Classical RK4 MUST request stage x-values:

```text
K1 state: 1
K2 state: 1.5
K3 state: 1.75
K4 state: 2.75
```

and produce:

```text
x(1) = 65/24 = 2.708333333333...
```

The required K4 stage value `2.75` independently catches the historical
half-step K4 defect, which would produce a different stage.

Tests MUST also directly verify the callback-visible stage times:

```text
t
t + h/2
t + h/2
t + h
```

rather than inferring time correctness only from a final result.

## 40. EB1.1 inertial-vacuum six-degree-of-freedom derivative evaluation

EB1.1 introduces the first physical rigid-body equations-of-motion evaluator in
the reconstructed BBTC external-ballistics subsystem.

The evaluator consumes one already-defined rigid-body state, projectile-property
record, reference-frame sample, and applied force/moment record and produces one
rigid-body state derivative.

EB1.1 deliberately evaluates the physical equations independently of numerical
integration. It does not advance simulation time or modify projectile state.

### 40.1 Scope

EB1.1 models rigid-projectile motion in vacuum in an inertial,
nonaccelerating, nonrotating active BBTC reference frame.

For EB1.1, "vacuum" means that no atmospheric or aerodynamic interaction is
present. Vacuum does NOT imply zero gravitational acceleration.

Therefore EB1.1 may include:

- physical gravitational-field acceleration supplied through B6;
- physical applied force supplied through B8; and
- physical applied moment supplied through B8.

EB1.1 does not include:

- atmosphere;
- wind;
- relative-air velocity;
- drag;
- lift;
- Magnus force or moment;
- aerodynamic damping;
- Coriolis acceleration;
- centrifugal acceleration;
- Euler reference-frame acceleration;
- reference-frame-origin translational acceleration;
- Eötvös-specific corrections;
- collision/contact response; or
- Cubes of Honor gameplay behavior.

Those effects remain later reviewed work.

### 40.2 Public header and evaluator families

EB1.1 introduces:

```text
include/bbtc/external_ballistics/inertial_vacuum.h
```

The external-ballistics umbrella header MUST include this header after EB1.1 is
implemented and accepted.

The precision-qualified evaluator functions are:

```c
bbtc_eb_inertial_vacuum_derivative_evaluate_float
bbtc_eb_inertial_vacuum_derivative_evaluate_double
bbtc_eb_inertial_vacuum_derivative_evaluate_long_double
```

Conceptually, each native-family function has the form:

```c
bbtc_status_e bbtc_eb_inertial_vacuum_derivative_evaluate_*(
    const bbtc_eb_rigid_body_state_*_t* state,
    const bbtc_eb_projectile_properties_*_t* projectile,
    const bbtc_eb_reference_frame_sample_*_t* reference_frame,
    const bbtc_eb_force_moment_*_t* force_moment,
    bbtc_eb_rigid_body_state_derivative_*_t* out_derivative
);
```

The exact parameter order is:

1. `state`;
2. `projectile`;
3. `reference_frame`;
4. `force_moment`;
5. `out_derivative`.

All inputs are borrowed and read-only.

The output is caller-owned writable storage.

The evaluator MUST NOT retain any supplied pointer after returning.

### 40.3 Input meanings

`state` is one complete B1/B2 rigid-body state.

`projectile` is one complete B3 rigid-projectile property record.

`reference_frame` is one complete B6 already-sampled reference-frame value.

`force_moment` is one complete B8 physical applied force/moment value.

`out_derivative` receives one complete B9 rigid-body state derivative.

EB1.1 performs no environment or reference-frame provider sampling itself.
Provider composition is deferred to a later EB1 checkpoint.

### 40.4 Inertial-reference restriction

EB1.1 supports only an inertial, nonaccelerating, nonrotating active reference
frame.

Consequently, after successful B6 validation, all components of the following
B6 vectors MUST compare equal to zero:

```text
reference_frame_origin_acceleration_reference_m_per_s2
reference_frame_angular_velocity_reference_rad_per_s
reference_frame_angular_acceleration_reference_rad_per_s2
```

Positive and negative floating zero both satisfy this requirement.

The B6 gravitational-acceleration vector is NOT required to be zero. Any finite
B6 gravitational-field acceleration remains physically valid for EB1.1.

If a valid B6 sample contains any nonzero origin-acceleration,
reference-frame-angular-velocity, or reference-frame-angular-acceleration
component, EB1.1 MUST return:

```text
BBTC_STATUS_UNSUPPORTED_MODEL_OR_OPTION
```

This result does not declare the B6 sample physically invalid. It means only
that the requested non-inertial reference-frame behavior belongs to a later
BBTC model.

EB1.1 MUST NOT silently ignore nonzero B6 frame kinematics.

### 40.5 Translational equations

Let:

```text
r_R = projectile center-of-mass position in active-reference coordinates
v_R = projectile center-of-mass velocity in active-reference coordinates
F_R = B8 applied physical force in active-reference coordinates
m   = B3 projectile mass
g_R = B6 physical gravitational-field acceleration
```

The translational position derivative is:

```text
dr_R/dt = v_R
```

The translational velocity derivative is:

```text
dv_R/dt = F_R / m + g_R
```

Gravity MUST remain separate from B8 applied force.

The evaluator MUST NOT transform `m * g_R` into B8 force or otherwise duplicate
gravity through the applied-force channel.

Because EB1.1 supports only an inertial reference frame, no reference-frame
origin, Coriolis, Euler, or centrifugal terms are added.

### 40.6 Quaternion kinematics

For EB1.1, `state->angular_velocity_body_rad_per_s` means projectile angular
velocity relative to the inertial active reference frame, expressed in
canonical BBTC projectile body coordinates.

Let the validated world/reference-from-body orientation be:

```text
q_WB
```

and let the body-frame angular velocity be:

```text
omega_B = (omega_x, omega_y, omega_z)
```

Define the corresponding pure quaternion:

```text
omega_B_quat = (omega_x, omega_y, omega_z, 0)
```

using BBTC quaternion storage order `(x, y, z, w)`.

The orientation derivative is:

```text
dq_WB/dt = 0.5 * q_WB * omega_B_quat
```

where `*` is the right-handed Hamilton quaternion product already frozen by the
BBTC external-ballistics mathematics contract.

The multiplication order is mandatory.

EB1.1 MUST NOT use:

```text
0.5 * omega_B_quat * q_WB
```

The implementation and tests MUST include an asymmetric orientation/angular-
velocity case for which these two products differ, so the historical legacy
multiplication-order defect cannot pass accidentally.

The B9 orientation derivative is a component-wise quaternion derivative and
MUST NOT be normalized by the EB1.1 evaluator.

### 40.7 Principal-axis Euler rotational dynamics

B3 establishes that the canonical BBTC body axes are principal axes through the
projectile center of mass for the current projectile representation.

Let:

```text
Ixx = projectile->principal_inertia.moment_about_x_kg_m2
Iyy = projectile->principal_inertia.moment_about_y_kg_m2
Izz = projectile->principal_inertia.moment_about_z_kg_m2
```

Let:

```text
omega_B = state->angular_velocity_body_rad_per_s
M_B     = force_moment->applied_moment_body_n_m
```

Then EB1.1 uses the rigid-body Euler equation:

```text
I * domega_B/dt + omega_B x (I * omega_B) = M_B
```

or equivalently:

```text
domega_B/dt =
    inverse(I) * (M_B - omega_B x (I * omega_B))
```

Because the current B3 inertia representation is diagonal in principal body
axes, the component equations are:

```text
domega_x/dt =
    (M_x - (Izz - Iyy) * omega_y * omega_z) / Ixx

domega_y/dt =
    (M_y - (Ixx - Izz) * omega_z * omega_x) / Iyy

domega_z/dt =
    (M_z - (Iyy - Ixx) * omega_x * omega_y) / Izz
```

EB1.1 MUST NOT assume axisymmetry.

In particular, `Iyy == Izz` is not required.

No full inertia-matrix inversion is required by EB1.1 because B3 already
guarantees strictly positive diagonal principal moments.

### 40.8 Output construction and numerical failure

EB1.1 MUST construct the complete derivative in local/internal storage before
committing it to caller-owned `out_derivative`.

The output fields are:

```text
orientation_world_from_body_derivative_per_s
position_derivative_reference_m_per_s
velocity_derivative_reference_m_per_s2
angular_velocity_derivative_body_rad_per_s2
```

After valid inputs have been accepted, generated arithmetic that cannot produce
a finite valid B9 derivative is an evaluator numerical failure.

Examples include overflow or invalid generated arithmetic during:

- applied-force division by mass;
- force-acceleration plus gravity;
- quaternion multiplication/scaling;
- inertia/angular-velocity products;
- gyroscopic cross-product evaluation; or
- Euler-equation division.

Before committing a generated derivative to caller-owned storage, EB1.1 MUST
validate the complete local derivative with the matching B9
`bbtc_eb_rigid_body_state_derivative_validate_*()` function.

Any non-success B9 validation result for this locally generated derivative is
an evaluator-generated numerical failure and MUST be mapped to
`BBTC_STATUS_NUMERICAL_FAILURE` rather than propagated as a caller-input status.

Such generated failures MUST return:

```text
BBTC_STATUS_NUMERICAL_FAILURE
```

and MUST leave `out_derivative` as the exact all-zero B9 derivative.

Generated arithmetic failure MUST NOT be reported as caller
`BBTC_STATUS_NAN_INPUT` or `BBTC_STATUS_NONFINITE_INPUT` after all public inputs
have already passed their matching validators.

### 40.9 Deterministic validation and failure precedence

If `out_derivative` is null, EB1.1 returns
`BBTC_STATUS_INVALID_ARGUMENT`.

When `out_derivative` is nonnull, the evaluator MUST first overwrite it with the
exact all-zero B9 derivative.

It then applies this exact validation order:

1. null `state`, `projectile`, `reference_frame`, or `force_moment` returns
   `BBTC_STATUS_INVALID_ARGUMENT`;
2. validate `state` with the matching B2 validator and propagate failure
   unchanged;
3. validate `projectile` with the matching B3 validator and propagate failure
   unchanged;
4. validate `reference_frame` with the matching B6 validator and propagate
   failure unchanged;
5. validate `force_moment` with the matching B8 validator and propagate failure
   unchanged;
6. reject valid but non-inertial B6 frame kinematics with
   `BBTC_STATUS_UNSUPPORTED_MODEL_OR_OPTION`;
7. evaluate the complete derivative in local/internal storage;
8. validate the complete locally generated derivative with the matching B9
   validator;
9. if generated arithmetic fails or B9 validation returns any non-success
   status, return `BBTC_STATUS_NUMERICAL_FAILURE`;
10. otherwise commit the validated derivative to `out_derivative` and return
    `BBTC_STATUS_SUCCESS`.

Validation precedence is therefore record-ordered. EB1.1 does not perform an
additional global NaN/infinity scan across otherwise independent public input
records before invoking their already-frozen validators.

Every failure after a nonnull output pointer is established leaves the exact
all-zero B9 derivative in caller storage.

### 40.10 Native precision, allocation, and determinism

Each EB1.1 evaluator family MUST remain entirely native:

- float inputs, operations, constants, and output remain native `float`;
- double inputs, operations, constants, and output remain native `double`; and
- long-double inputs, operations, constants, and output remain native
  `long double`.

One precision family MUST NOT route arithmetic through another.

EB1.1 requires no dynamic allocation.

It performs no file I/O, process termination, global mutable-state update,
provider dispatch, trajectory allocation, collision query, Cubes of Honor
conversion, or gameplay operation.

For identical native-family inputs and the same floating-point environment, the
evaluator has no hidden history and is deterministic.

### 40.11 Relationship to B10 and B11

EB1.1 is the physical equation evaluator below the generic B10 derivative-
provider boundary.

A later EB1 checkpoint may expose EB1.1 through a concrete B10 callback whose
borrowed context supplies projectile properties, reference-frame sampling, and
physical loading.

That later composition layer may query B7 using each B10 candidate state's

## 42. EB1.2 inertial-vacuum derivative-provider composition

EB1.2 composes the already accepted EB1.1 physical equations of motion with the
already accepted B7 reference-frame provider and B10 state-derivative provider
boundaries.

The purpose of EB1.2 is not to introduce new rigid-body physics. Its purpose is
to expose EB1.1 through an ordinary B10 provider so the unchanged B11 integrator
can request stage-local physical derivatives while B7 samples gravity and
reference-frame state at each candidate position and simulation time.

### 42.1 Scope

EB1.2 provides one concrete inertial-vacuum B10 composition layer.

It combines:

- one immutable-during-use B3 projectile-property value;
- one immutable-during-use constant B8 applied force/moment value;
- one B7 reference-frame provider descriptor;
- one validated B2 candidate state supplied by B10; and
- the accepted EB1.1 inertial-vacuum derivative evaluator.

EB1.2 does not change the equations frozen by EB1.1 and does not change B7,
B10, or B11 semantics.

The normal ballistic-vacuum configuration uses an all-zero B8 force/moment
record. A nonzero constant B8 record remains valid when a caller deliberately
wants a constant non-aerodynamic physical force or moment.

EB1.2 does not introduce a time-varying, position-varying, state-varying, or
callback-driven force/moment model.

### 42.2 Public header, configuration records, and functions

EB1.2 introduces:

```text
include/bbtc/external_ballistics/inertial_vacuum_provider.h
```

After EB1.2 implementation is accepted, the external-ballistics umbrella header
MUST include this header.

The three public configuration types are:

```c
bbtc_eb_inertial_vacuum_provider_config_float_t
bbtc_eb_inertial_vacuum_provider_config_double_t
bbtc_eb_inertial_vacuum_provider_config_long_double_t
```

Conceptually, each native-family record has exactly these members in this order:

```c
typedef struct bbtc_eb_inertial_vacuum_provider_config_*_t
{
    bbtc_eb_projectile_properties_*_t projectile;
    bbtc_eb_force_moment_*_t constant_force_moment;
    bbtc_eb_reference_frame_provider_*_t reference_frame_provider;
}
bbtc_eb_inertial_vacuum_provider_config_*_t;
```

`projectile` is stored by value.

`constant_force_moment` is stored by value and is used unchanged for every
derivative request made through the bound provider.

`reference_frame_provider` is stored by value. Its own `context` member retains
the B7 borrowed-context semantics already frozen by EB0.1-B7.

EB1.2 introduces these validation functions:

```c
bbtc_eb_inertial_vacuum_provider_config_validate_float
bbtc_eb_inertial_vacuum_provider_config_validate_double
bbtc_eb_inertial_vacuum_provider_config_validate_long_double
```

and these binding functions:

```c
bbtc_eb_inertial_vacuum_provider_bind_float
bbtc_eb_inertial_vacuum_provider_bind_double
bbtc_eb_inertial_vacuum_provider_bind_long_double
```

Conceptually, the bind functions have the form:

```c
bbtc_status_e bbtc_eb_inertial_vacuum_provider_bind_*(
    const bbtc_eb_inertial_vacuum_provider_config_*_t* config,
    bbtc_eb_state_derivative_provider_*_t* out_provider
);
```

The exact parameter order is:

1. `config`;
2. `out_provider`.

EB1.2 does not expose a second integrator and does not expose a public
model-specific derivative callback separate from the generic B10 descriptor.

### 42.3 Configuration validation

The EB1.2 configuration validators are read-only.

They apply this exact validation order:

1. null `config` returns `BBTC_STATUS_INVALID_ARGUMENT`;
2. validate `config->projectile` with the matching B3 validator and propagate
   failure unchanged;
3. validate `config->constant_force_moment` with the matching B8 validator and
   propagate failure unchanged;
4. require `config->reference_frame_provider.sample` to be nonnull, otherwise
   return `BBTC_STATUS_INVALID_ARGUMENT`;
5. otherwise return `BBTC_STATUS_SUCCESS`.

A null B7 provider `context` is valid.

Configuration validation MUST NOT invoke the B7 callback and therefore cannot
validate any future B6 sample.

Configuration validation MUST NOT alter the configuration or the object reached
through the B7 provider context.

### 42.4 Binding semantics

If `out_provider` is null, a bind function returns
`BBTC_STATUS_INVALID_ARGUMENT`.

When `out_provider` is nonnull, the bind function MUST first overwrite it with
the zero-initialized matching B10 provider descriptor, such that
`out_provider->evaluate == NULL` and `out_provider->context == NULL`.

This requirement is semantic rather than a byte-representation guarantee. C
does not require a null function pointer or null object pointer to have an
all-bits-zero representation.

The bind function then:

1. rejects null `config` with `BBTC_STATUS_INVALID_ARGUMENT`;
2. validates `config` with the matching EB1.2 configuration validator and
   propagates failure unchanged;
3. initializes `out_provider->evaluate` to the BBTC-owned EB1.2 derivative
   callback for the matching native family;
4. initializes `out_provider->context` to exactly the supplied `config`
   pointer; and
5. returns `BBTC_STATUS_SUCCESS`.

Every bind failure after a nonnull output pointer has been established leaves
the zero-initialized B10 provider descriptor in caller storage, with
`evaluate == NULL` and `context == NULL`.

Binding performs no allocation and copies none of the configuration into hidden
BBTC-owned storage.

### 42.5 Ownership and lifetime

A bound EB1.2 B10 provider borrows the exact configuration object supplied to
the bind function.

The caller MUST keep that configuration object alive for every evaluation made
through the bound B10 descriptor.

The caller MUST NOT modify the configuration object while the bound provider is
being evaluated or while a B11 step using that provider is in progress.

Copying a configuration object after binding does not retarget an already-bound
provider. The provider remains bound to the exact object whose address was
supplied to the successful bind call.

The B7 provider context nested inside the configuration remains caller-owned and
MUST satisfy the B7 lifetime and repeated/out-of-order-call requirements.

The nested B7 provider context MUST NOT provide writable aliasing access to the
bound EB1.2 configuration object or to any of its by-value members while a
derivative evaluation or B11 step is in progress. Such aliasing could otherwise
allow the B7 callback to mutate already-validated projectile, force/moment, or
provider configuration during one derivative request.

When an EB1.2 provider is used by B11, neither the EB1.2 configuration nor the
nested B7 provider context may provide writable aliasing access to the
caller-owned B11 state in a way that violates B11 transactional semantics.

Invoking the caller-supplied B7 callback MAY produce caller-owned context side
effects such as diagnostics, counters, or request recording, provided those
side effects do not violate the already accepted B7 requirements or determine
physical sample meaning from call order. EB1.2 itself does not write through
the opaque B7 context pointer.

Such B7 context side effects are not transactional. EB1.2, B10, and B11 do not
roll them back if a later B7, EB1.1, B10, or B11 operation fails.

EB1.2 allocates, frees, retains, clones, or otherwise owns none of these caller
objects.

### 42.6 Derivative-request composition

The bound EB1.2 provider MUST be consumed through the already accepted B10
dispatch interface.

For one B10 callback request with candidate state `state`, EB1.2 performs this
composition in the matching native precision family:

1. validate the bound EB1.2 configuration;
2. call the matching B7 provider-dispatch function with:
   - `&state->position_m` as the requested active-reference position; and
   - `state->time_s` as the requested simulation time;
3. if B7 succeeds, receive one complete validated local B6 sample;
4. call the matching EB1.1 evaluator with:
   - the same candidate `state`;
   - `&config->projectile`;
   - the local B6 sample;
   - `&config->constant_force_moment`; and
   - the B10 callback derivative output; and
5. return the resulting status.

EB1.2 MUST NOT substitute the initial-state position or time for the supplied
candidate state's position or time.

EB1.2 MUST NOT cache a B6 sample across distinct derivative requests.

EB1.2 MUST NOT sample B4/B5 environment data.

EB1.2 MUST NOT alter the candidate state, projectile properties, constant B8
record, B7 provider descriptor, or B7 provider context.

### 42.7 Stage-local B7 sampling

When a bound EB1.2 provider is used through B11 RK4, each B10 derivative request
causes a fresh B7 dispatch using that candidate stage state's position and
`state->time_s`.

For a successful B11 step, this means exactly four EB1.2 derivative callbacks
and therefore exactly four B7 sampling requests: one each for K1, K2, K3, and
K4.

EB1.2 places no requirement that those four sampled positions be distinct.

For classical RK4 with a synthetic constant-velocity, zero-acceleration,
zero-angular-velocity case, tests MUST independently verify that B7 observes:

```text
K1: r0             at t
K2: r0 + v*h/2     at t + h/2
K3: r0 + v*h/2     at t + h/2
K4: r0 + v*h       at t + h
```

for exactly representable test values.

This test establishes composition and stage-local sampling behavior. It does not
replace the direct EB1.1 equation tests and is not the complete EB1 analytic
trajectory-validation milestone.

A test-only B7 provider MAY record requests for observation, but its returned
physical sample MUST remain a deterministic function of its request and
configured test data rather than depending on call order for physical meaning.

### 42.8 Failure propagation

Configuration-validation failures are returned before B7 is called.

A B7 provider-dispatch failure is propagated unchanged by EB1.2.

When B7 fails, EB1.2 MUST NOT invoke EB1.1 for that derivative request.

If B7 succeeds but the resulting valid B6 sample contains nonzero frame
kinematics unsupported by EB1.1, the EB1.1
`BBTC_STATUS_UNSUPPORTED_MODEL_OR_OPTION` result is propagated unchanged.

Any EB1.1 input or numerical failure is propagated unchanged by EB1.2.

B10 remains authoritative for its existing fail-closed callback-output
semantics. A callback failure returned by EB1.2 therefore leaves the public B10
dispatch output as the exact all-zero B9 derivative.

When B11 consumes the bound B10 provider, any propagated EB1.2/B7/EB1.1 failure
retains the already accepted B11 transactional rule: the caller-owned state is
not committed on failure.

That caller-state transaction does not extend to side effects already produced
inside the caller-owned B7 provider context. Such side effects are not rolled
back.

EB1.2 does not invent replacement statuses for valid B7 or EB1.1 failures.

### 42.9 Relationship to B7, B10, and B11

B7 remains the only reference-frame sampling boundary used by EB1.2.

B10 remains the only derivative-provider dispatch boundary presented to B11.

B11 remains unchanged and physics-agnostic.

The intended composition is:

```text

                -> B9 derivative
```

EB1.2 MUST NOT add a direct B11 dependency to EB1.1 or B7.

EB1.2 MUST NOT modify the B11 stage equations, quaternion stage-normalization
rules, step acceptance rules, or transactional semantics.

### 42.10 Native precision, allocation, and determinism

Every EB1.2 family remains native `float`, `double`, or `long double`
throughout configuration storage, B7 sampling, EB1.1 evaluation, and B10
output.

One precision family MUST NOT route through another.

EB1.2 itself introduces no mutable global state and no hidden sampling cache or
call history.

## 44. EB1.3 analytic end-to-end propagation validation

EB1.3 is a validation milestone for the already accepted EB1.1 physical
equations, EB1.2 B7/B10 composition, and B11 fixed-step RK4 integrator.

EB1.3 does not introduce a new production physics model, provider boundary,
integrator, trajectory container, or public propagation API. Its purpose is to
demonstrate that the complete accepted inertial-vacuum pipeline reproduces
independent analytic solutions and exhibits the expected fourth-order
convergence where the exact solution is not a low-degree polynomial.

The pipeline under validation is:

```text
test-owned initial state and configuration
    -> B11 fixed-step RK4
        -> B10 state-derivative dispatch
            -> EB1.2 inertial-vacuum provider
                -> B7 reference-frame sampling
                -> EB1.1 inertial-vacuum derivative evaluation
                    -> B9 derivative
```

### 44.1 Scope and implementation surface

The intended EB1.3 implementation is validation-only.

The dedicated validation source is:

```text
tests/test_eb_inertial_vacuum_propagation.c
```

and the CTest name is:

```text
bbtc.eb_inertial_vacuum_propagation
```

`tests/CMakeLists.txt` may be changed only as needed to register that test.

No production header or production source file is required to change for EB1.3
when the already accepted implementation satisfies the analytic oracles.

A test-local helper MAY advance a state through `N` successive calls to the
matching B11 fixed-step RK4 function. Such a helper is test infrastructure and
does not create a public multi-step propagation API.

If EB1.3 validation exposes a genuine defect in a sealed EB1.1, EB1.2, or B11
production implementation, that defect MUST be reviewed explicitly before the
sealed production code is modified. A failing validation result alone is not
permission to weaken an oracle or silently change an accepted contract.

### 44.2 Independence of analytic oracles

Expected analytic states MUST be computed independently of BBTC's derivative
and integration implementations.

The analytic oracle MUST NOT:

- call EB1.1 to manufacture expected derivatives;
- call B10 or B11 to manufacture expected states;
- copy expected values from BBTC output;
- reuse B11 stage values as the reference solution; or
- derive acceptance thresholds from the observed BBTC error.

Elementary arithmetic and the matching native C math-library functions are
permitted. In particular, the three precision families use the corresponding
`float`, `double`, or `long double` arithmetic and matching transcendental
functions such as `sinf`/`cosf`, `sin`/`cos`, and `sinl`/`cosl`.

One precision family's oracle MUST NOT route through another precision family.

### 44.3 Common physical restrictions

Every EB1.3 case remains within the accepted EB1.1 inertial-frame restriction.

Therefore every successful B7 sample has exact zero:

- frame-origin acceleration;
- reference-frame angular velocity; and
- reference-frame angular acceleration.

Only true gravitational acceleration may vary through B7.

Unless a case explicitly requires a constant B8 force, the B8 force/moment
record is all zero.

Rotational analytic cases use a spherical principal inertia tensor so zero
applied moment produces constant body angular velocity without gyroscopic
coupling.

Every run begins from a fresh valid B2 state, fresh EB1.2 configuration, and
fresh test-owned B7 context. Results from one step-size run MUST NOT become the
initial state of another convergence run.

### 44.4 Precision-qualified comparison rule for polynomial cases

The drift and constant-acceleration cases are analytically polynomial and are
not required to compare bit-for-bit because B11 includes native floating-point
RK4 weighting and quaternion normalization.

For one scalar family with machine epsilon `epsilon_family`, a finite scalar
result `actual` satisfies the EB1.3 polynomial comparison when:

```text
abs(actual - expected)
    <= 4096 * epsilon_family * max(1, abs(expected))
```

using native-family arithmetic.

The matching `FLT_EPSILON`, `DBL_EPSILON`, or `LDBL_EPSILON` is used for the
family under test.

This tolerance is a validation allowance for floating-point evaluation order;
it does not redefine any public BBTC physical or numerical contract.

### 44.5 Oracle A: multi-step inertial drift

All three native precision families MUST validate a multi-step zero-acceleration
drift case through the complete EB1.2/B10/B11 pipeline.

The case uses:

```text
initial position     r0 = ( 1, -2,  3) m
initial velocity     v0 = ( 4, -6,  8) m/s
initial orientation  q0 = ( 0,  0,  0, 1)
initial angular vel. w0 = ( 0,  0,  0) rad/s
B7 gravity           g  = ( 0,  0,  0) m/s^2
B8 force/moment         = all zero
initial time         t0 = 0 s
step size             h = 0.25 s
step count            N = 8
final time             T = 2 s
```

The independent analytic solution is:

```text
v(T) = v0
r(T) = r0 + v0*T = (9, -14, 19) m
q(T) = q0
w(T) = w0
```

The final state MUST satisfy the comparison rule in 44.4 and the public B2
validator.

The B7 test context MUST observe exactly `4*N = 32` sampling requests during the
successful propagation.

### 44.6 Oracle B: multi-step constant acceleration from B7 plus B8

All three native precision families MUST validate a case in which constant
gravity and constant applied force combine through EB1.1.

The case uses a projectile mass of exactly `2 kg` and:

```text
initial position     r0 = (1,  2, 3) m
initial velocity     v0 = (4, -2, 1) m/s
initial orientation  q0 = (0, 0, 0, 1)
initial angular vel. w0 = (0, 0, 0) rad/s

B7 gravity           g  = (0.5,  1, -1) m/s^2
B8 applied force     F  = (2,   -4,  6) N
B8 applied moment       = (0,    0,  0) N*m

initial time         t0 = 0 s
step size             h = 0.25 s
step count            N = 8
final time             T = 2 s
```

The expected constant translational acceleration is:

```text
a = g + F/m = (1.5, -1, 2) m/s^2
```

and the independent analytic final state is:

```text
v(T) = v0 + a*T
     = (7, -4, 5) m/s

r(T) = r0 + v0*T + 0.5*a*T^2
     = (12, -4, 9) m
```

Orientation and angular velocity remain unchanged.

The final state MUST satisfy the comparison rule in 44.4 and the public B2
validator.

The B7 test context MUST observe exactly 32 sampling requests.

### 44.7 Oracle C: position-dependent gravity and RK4 convergence

All three native precision families MUST validate stage-local position sampling
with a synthetic but physically well-defined one-dimensional restoring gravity
field:

```text
g_x(x) = -x  m/s^2
g_y    =  0
g_z    =  0
```

for positions whose numeric x-coordinate is expressed in metres. Equivalently,
the restoring coefficient is exactly `1 s^-2`.

The initial translational state is:

```text
x(0)  = 1 m
v_x(0)= 0 m/s
```

with all other position and velocity components zero. Orientation is identity,
angular velocity is zero, and B8 is all zero.

The exact solution at `T = 1 s` is:

```text
x(T)   = cos(1) m
v_x(T) = -sin(1) m/s
```

using the matching native-family trigonometric functions for the oracle.

Three independent propagations are performed over the same interval with:

```text
h0 = 1.0  s   -> 1 step
h1 = 0.5  s   -> 2 steps
h2 = 0.25 s   -> 4 steps
```

The coarsest run deliberately remains within a numerically useful error regime,
while the finest run stays far enough above single-precision roundoff that the
required convergence-ratio check retains practical margin across conforming
platforms.

For each run define the native-family translational error:

```text
e(h) = max(
    abs(x_numeric(T)   - x_exact(T)),
    abs(vx_numeric(T)  - vx_exact(T))
)
```

Each error MUST be finite and strictly positive, and:

```text
e(h0) > e(h1) > e(h2)
e(h0) / e(h1) >= 10
e(h1) / e(h2) >= 10
```

The ratio floor is an end-to-end regression criterion consistent with
fourth-order convergence while leaving margin for native-family floating-point
rounding. It is not a replacement definition of RK4 order.

The corresponding B7 contexts MUST observe exactly 4, 8, and 16 sample
requests.

This oracle specifically guards against replacing stage-local B7 sampling with
one gravity sample per completed timestep.

### 44.8 Oracle D: noncommuting pure principal-axis spin and quaternion convergence

All three native precision families MUST validate rotational propagation with:

```text
q_WB(0) = (0, 0, 1, 0)
w_B     = (1, 0, 0) rad/s
```

The initial quaternion is the exact unit quaternion for a 180-degree
world-from-body rotation about +Z. The projectile uses a spherical inertia
tensor, zero applied moment, zero applied force, and zero gravity.

The non-identity initial orientation is deliberate. It does not commute with
the pure +X angular-velocity quaternion, so the accepted right-multiplied
Hamilton kinematics are distinguishable from the historical wrong
left-multiplied ordering.

The exact angular velocity remains constant.

At `T = 1 s`, under the accepted active Hamilton world-from-body convention and
EB1.1 equation

```text
dq_WB/dt = 0.5 * q_WB * omega_B_quat
```

define the exact +X spin increment:

```text
q_spin(T) = (sin(0.5), 0, 0, cos(0.5))
```

The accepted multiplication order gives:

```text
q_exact(T)
    = q_WB(0) * q_spin(T)
    = (0, sin(0.5), cos(0.5), 0)
```

For comparison, the historical wrong ordering would give:

```text
q_wrong(T)
    = q_spin(T) * q_WB(0)
    = (0, -sin(0.5), cos(0.5), 0)
```

`q_wrong(T)` is not sign-equivalent to `q_exact(T)`. Therefore this oracle MUST
fail for that multiplication-order regression rather than merely checking a
case in which left and right multiplication happen to commute.

The same three step sizes are used:

```text
h0 = 1.0  s
h1 = 0.5  s
h2 = 0.25 s
```

Quaternion comparison MUST be sign-invariant. For numerical quaternion `q_n`
and analytic quaternion `q_e`, define:

```text
d_plus  = max_i abs(q_n[i] - q_e[i])
d_minus = max_i abs(q_n[i] + q_e[i])
e_q(h)  = min(d_plus, d_minus)
```

Each quaternion error MUST be finite and strictly positive, and:

```text
e_q(h0) > e_q(h1) > e_q(h2)
e_q(h0) / e_q(h1) >= 10
e_q(h1) / e_q(h2) >= 10
```

Every final angular-velocity component MUST satisfy the comparison rule in
44.4, translational state must remain unchanged within that rule, and every
final state MUST pass the public B2 validator.

The corresponding B7 contexts MUST observe exactly 4, 8, and 16 sample
requests for the three step-size runs.

This oracle validates the accepted quaternion multiplication order together
with B11 stage/final normalization rather than an unconstrained quaternion RK4
scheme.

### 44.9 Failure behavior and determinism

EB1.3 introduces no new failure statuses.

A propagation helper stops immediately when any B11 step returns non-success
and returns that status to the test caller without attempting later steps.

Analytic success cases use deterministic B7 providers whose physical sample is
a pure function of the requested position and configured immutable test data.
Diagnostic request counters are permitted as caller-owned B7 context side
effects and remain nontransactional exactly as accepted by EB1.2.

No oracle may depend on B7 call order to determine the returned physical field.

### 44.11 Deliberately deferred behavior

EB1.3 does NOT define or validate:

- atmosphere or wind;
- aerodynamic drag, lift, Magnus force, or aerodynamic moments;
- ballistic-coefficient models;
- rotating-reference-frame acceleration equations;
- Coriolis or centrifugal effects;
- adaptive integration or local error control;
- public multi-step trajectory storage;
- interpolation or dense output;
- event detection;
- collision/contact response;
- Cubes of Honor adapter behavior; or
- a replacement integrator.

Those remain later external-ballistics milestones.
