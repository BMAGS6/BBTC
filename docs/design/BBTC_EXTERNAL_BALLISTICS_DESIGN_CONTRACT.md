# BBTC External Ballistics Design Contract

**Contract version:** 0.1.2

**Project phase:** EB0.1-B2

**Applies to:** `rewrite/eb0_1b2_math_validation_v1`

**Status:** Accepted

**Date:** 2026-11-26

## 1. Purpose

This document defines the engineering architecture for external ballistics in
BMAGS' Ballistic Trajectory Calculator (BBTC).

The external-ballistics subsystem is designed as an independent C23 library
component suitable for standalone scientific use and direct integration into
Cubes of Honor.

This contract supplements the accepted
`docs/design/BBTC_DESIGN_CONTRACT.md`. Generic requirements defined by that
contract remain applicable unless this document explicitly replaces them for
external-ballistics work.

Internal ballistics is not a dependency of external ballistics. A caller MAY
supply a muzzle state produced by a BBTC internal-ballistics model, but the
external-ballistics API MUST also accept a complete caller-supplied initial
projectile state without requiring any internal-ballistics component.

The words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** state
requirements.

## 2. Architectural goals

The external-ballistics subsystem MUST:

- model projectile flight as a reusable physics library rather than as gameplay
  logic;
- support six-degree-of-freedom rigid-body dynamics from the architectural
  foundation;
- remain independent of Cubes of Honor source types and subsystems;
- integrate cleanly with Cubes of Honor through explicit adapter code;
- use SI units throughout its public physics API and computational core;
- retain BBTC's `float`, `double`, and `long double` scalar families;
- make reference-frame, orientation, and angular-velocity conventions explicit;
- obtain atmosphere and environmental state through caller-controlled
  interfaces rather than requiring a BBTC-owned world or weather system;
- separate numerical integration from aerodynamic force and moment models;
- permit progressively higher-fidelity physical models without changing the
  fundamental state representation; and
- preserve deterministic diagnostics and fail-closed validation behavior
  consistent with the existing BBTC design contract.

External-ballistics architecture MUST NOT assume that every consumer is a game,
that every consumer uses Earth, or that every initial projectile state was
generated by BBTC internal ballistics.

## 3. Ownership boundary

BBTC external ballistics owns:

- projectile rigid-body state;
- translational and rotational equations of motion;
- aerodynamic force and moment evaluation;
- relative-air velocity;
- Mach-dependent ballistic calculations;
- numerical integration of projectile state;
- applicable rotational, gyroscopic, aerodynamic, and reference-frame effects;
- numerical and physical-model diagnostics; and
- interpolation or trajectory-state information required to expose the
  calculated flight path.

The host application owns:

- world geometry;
- terrain and object collision;
- game entities;
- rendering;
- audiovisual effects;
- networking and replication;
- damage and gameplay consequences;
- world-unit conventions;
- atmospheric or weather simulation when supplied by the host; and
- conversion between host-specific types and BBTC public types.

BBTC MUST NOT depend on Cubes of Honor headers.

Cubes of Honor integration MUST occur through an adapter owned by Cubes of
Honor.

## 4. Units

The external-ballistics API uses SI units consistently with the parent BBTC
design contract.

Relevant quantities include:

| Quantity | Canonical unit |
| --- | --- |
| Position / displacement | m |
| Velocity | m/s |
| Acceleration | m/s² |
| Time | s |
| Mass | kg |
| Force | N |
| Moment / torque | N·m |
| Angular velocity | rad/s |
| Moment of inertia | kg·m² |
| Pressure | Pa |
| Temperature | K |
| Density | kg/m³ |
| Speed of sound | m/s |

Host-specific units MUST be converted at the integration boundary.

## 5. Scalar precision

External ballistics MUST provide first-class native implementations for:

- `float`;
- `double`; and
- `long double`.

The scalar-family rules of the parent BBTC contract remain applicable.

The `double` family SHOULD remain the principal validation and reference family.

A performance-sensitive consumer such as Cubes of Honor MAY use the `float`
family, the `double` family, or another supported family through explicit
precision-qualified APIs.

The choice of runtime precision in Cubes of Honor MUST NOT alter the public ABI
of another BBTC precision family.

### 5.1 Mathematical value types

BBTC MUST own the mathematical value types required to state its public physics
contracts. The external-ballistics API MUST NOT depend on Cubes of Honor vector,
quaternion, matrix, or other engine-math declarations.

The first external-ballistics math boundary SHOULD remain deliberately small.
It MUST provide precision-qualified three-dimensional vector and quaternion
value records sufficient to represent projectile state, environmental vectors,
forces, moments, and orientations. Equivalent `float`, `double`, and
`long double` records MUST follow the scalar-family requirements of the parent
contract.

These BBTC records are physics-interface types, not the beginning of a competing
general-purpose graphics or game-engine mathematics library. Operations required
by the solver, such as vector addition, subtraction, scaling, dot products,
cross products, norms, normalization, quaternion products, conjugation,
normalization, and vector rotation, MAY remain internal implementation helpers
until a concrete public use justifies exposing them.

EB0 does not require a public four-by-four matrix abstraction. Rendering,
projection, camera, and scene-transform matrices remain host responsibilities.
Rigid-body inertia MUST be represented using physical moments or an explicitly
defined physical inertia tensor rather than by reusing a graphics-oriented
matrix type.

BBTC quaternion mathematics MUST use an active, right-handed Hamilton-product
convention. A BBTC orientation quaternion is written conceptually as
`q = (x, y, z, w)`, where `w` is the scalar component and `(x, y, z)` is the
vector component. For a unit world-from-body quaternion `q_WB`, a body-frame
vector `v_B` is rotated into the world/reference frame by the active rotation

`v_W = q_WB * (0, v_B) * inverse(q_WB)`.

For a unit quaternion, the inverse is the conjugate. Exact public record names,
declaration order, ABI layout, and which low-level operations are exposed remain
deferred to their dedicated EB0 implementation checkpoints.

A host MUST NOT replace BBTC mathematical types through preprocessor aliases,
build definitions, typedef substitution, or other configuration that changes
the meaning or ABI of the BBTC public headers.

### 5.2 Cubes of Honor precision and conversion boundary

Cubes of Honor currently uses float-oriented engine math, while BBTC supports
three native scalar families. This difference MUST be handled explicitly at the
adapter boundary rather than by coupling the two type systems.

The initial Cubes of Honor integration SHOULD use the BBTC `double` family for
projectile state and numerical integration unless profiling demonstrates that a
different family provides a material gameplay benefit. Cubes of Honor MAY
continue to use its existing `float` vectors, quaternions, matrices, atmosphere
records, rendering state, and collision data.

The Cubes of Honor adapter MUST perform explicit value conversion when data
crosses the boundary. For example, a Cubes of Honor `vec3f_t` supplied to a
BBTC `double` simulation is converted component-by-component to the
corresponding BBTC double vector. BBTC output needed by the game is converted
back explicitly to the host representation.

Such conversion helpers SHOULD be small, inlineable, deterministic functions.
Their performance SHOULD be measured if they ever appear material in profiling,
but layout coincidence MUST NOT be used as a reason to bypass the language type
system.

## 6. Reference-frame model

BBTC external ballistics uses an explicitly defined right-handed reference frame.

The BBTC core MUST NOT assign intrinsic geographic meanings such as east,
north, south, or up to the three coordinate axes.

A host adapter MAY map the BBTC reference frame directly to an application
coordinate system when their handedness and axis meanings are compatible.

Position and translational velocity are expressed in the active reference
frame.

The initial integration origin SHOULD normally be local to the projectile launch
state rather than an unnecessarily large absolute world coordinate.

For Cubes of Honor, the intended integration origin is the muzzle position.
BBTC therefore begins projectile displacement at or near the local origin, and
the Cubes of Honor adapter reconstructs world-space position from the stored
muzzle origin plus the BBTC displacement.

## 7. Rigid-body state

The six-degree-of-freedom architecture MUST represent at least:

- simulation time;
- three-dimensional position;
- three-dimensional translational velocity;
- orientation as a unit quaternion; and
- three-dimensional angular velocity.

Euler angles MUST NOT be used as the integrated orientation state.

The quaternion represents **world-from-body** orientation: it transforms a
vector expressed in projectile body coordinates into the active reference
frame.

Angular velocity is expressed in the **projectile body frame**.

Quaternion normalization and integration behavior MUST be specified and tested
before the first rotational integrator is accepted.

The exact public record names and field layout are deferred to a later EB0
implementation checkpoint.

## 8. Projectile body frame

The canonical BBTC projectile body frame is right-handed and uses the following
axis meanings:

- `+X` is forward, from the projectile center of mass toward the nose;
- `+Y` is body-right; and
- `+Z` is body-down.

Positive angular quantities follow the right-hand rule about their corresponding
positive body axes. The longitudinal or roll axis is `+X`, the pitch axis is
`+Y`, and the yaw axis is `+Z`.

This convention is selected for physical clarity and compatibility with common
rigid-body and flight-dynamics formulations. It is intentionally independent of
a host application's camera, renderer, model-authoring, or world-axis
conventions.

For an axisymmetric projectile whose center of mass lies on the longitudinal
axis, `Ixx` denotes the axial moment of inertia and `Iyy` and `Izz` denote the
transverse moments. An axisymmetric model may require `Iyy == Izz`, but the
architecture MUST NOT assume that equality for every future rigid body.

A host whose local forward direction differs from BBTC `+X` MUST perform one
explicit, documented basis conversion at the adapter boundary. Host conventions
MUST NOT leak into BBTC aerodynamic coefficient definitions or rigid-body
equations.

## 9. Projectile physical properties

The architecture MUST support rigid-body projectile properties sufficient for
six-degree-of-freedom dynamics, including:

- mass;
- center-of-mass-related geometry required by implemented models;
- moments of inertia;
- aerodynamic reference dimensions; and
- aerodynamic-model data.

An axisymmetric projectile MAY use an optimized representation based on axial
and transverse moments of inertia where physically appropriate.

The architecture MUST NOT prevent a later general inertia representation.

Aerodynamic coefficient models and projectile geometry MUST remain logically
separate from the integrated dynamic state.

## 10. Environmental sampling

External ballistics MUST obtain local environmental conditions through an
explicit caller-controlled interface.

The environment interface MUST be capable of supplying, as applicable:

- air temperature;
- absolute pressure;
- air density;
- local speed of sound; and
- wind velocity.

Sampling MUST accept projectile position and simulation time so that a host can
provide altitude-dependent, position-dependent, or time-dependent conditions.

The integrator MUST permit environmental sampling at derivative-evaluation
points, including intermediate integration stages. A host environment MUST NOT
be restricted to one sample per render frame or one sample per complete
integration step.

BBTC MUST NOT require Cubes of Honor's atmosphere implementation.

The Cubes of Honor adapter is expected to obtain atmospheric state from the
authoritative Cubes of Honor atmosphere subsystem and translate the result into
the corresponding BBTC environment sample.

A standalone BBTC application MAY provide constant-atmosphere, standard-
atmosphere, table-driven, or other environment-provider helpers. Such helpers
MUST remain optional clients of the same environment contract used by hosted
applications; the core external-ballistics solver MUST NOT require one specific
BBTC-owned atmosphere implementation.

## 11. Reference-frame acceleration and rotation

Gravity MUST be supplied through an explicit physical/reference-frame contract
rather than assumed to have a fixed hard-coded axis.

The architecture SHOULD support a supplied planetary/reference-frame angular
velocity vector for effects associated with a rotating reference frame.

This permits the same BBTC solver architecture to represent Earth-like,
non-Earth, artificial, reduced-gravity, and game-specific environments.

Coriolis or related rotating-frame terms MUST NOT be introduced until the
meaning of the supplied reference frame and velocity state is formally fixed
and independently tested.

## 12. Numerical architecture

The numerical integrator MUST be separable from the physical force and moment
model.

Conceptually, state evolution follows:

- translational position derivative from translational velocity;
- translational velocity derivative from net force and mass;
- rotational dynamics from applied moments and rigid-body inertia; and
- quaternion evolution from the defined orientation and angular-velocity
  convention.

For the frozen world-from-body orientation `q_WB` and body-frame angular
velocity `omega_B`, the quaternion differential equation uses the Hamilton
composition

`dq_WB/dt = 0.5 * q_WB * omega_B_quat`,

where `omega_B_quat` is the pure quaternion whose vector part is `omega_B` and
whose scalar part is zero. The first rotational implementation MUST validate
this convention independently rather than relying only on visually plausible
orientation behavior.

Quaternion normalization or constraint-control strategy MUST be documented and
tested. Renormalization MAY control ordinary numerical drift, but it MUST NOT be
used to silently accept a nonfinite, zero-length, or otherwise invalid
orientation supplied at a public validation boundary.

The first correctness-oriented implementation MAY use a fixed-step
fourth-order Runge-Kutta method.

Future adaptive, game-oriented, or specialized rotational integrators MUST be
able to use the same physical state and force/moment contracts without replacing
the external-ballistics architecture.

## 13. Cubes of Honor integration boundary

BBTC MUST remain usable as an ordinary standalone library through the
`bbtc::bbtc` CMake target.

Cubes of Honor SHOULD consume BBTC as a Git submodule and CMake subproject
rather than compiling BBTC source files directly into its own source list.

The Cubes of Honor adapter is responsible for:

- conversion between Cubes of Honor vector/quaternion types and BBTC types;
- conversion between Cubes of Honor world scale and SI meters;
- construction of the muzzle-relative initial state;
- sampling the Cubes of Honor atmosphere at the projectile location;
- supplying gravity and other reference-frame information;
- converting calculated BBTC positions back to Cubes of Honor world space; and
- passing calculated trajectory segments to Cubes of Honor collision systems.

The adapter MUST NOT type-pun or pointer-cast distinct Cubes of Honor and BBTC
structure types merely because their layouts happen to match.

Explicit field-wise conversion is required unless a future shared ABI contract
states otherwise.

### 13.1 Cubes of Honor math and basis adapter

Cubes of Honor and BBTC intentionally retain separate mathematical type systems.
The adapter MUST translate values between them; neither project is required to
adopt the other's complete math library.

The currently established Cubes of Honor local camera/player basis uses:

- `+X` as local right;
- `+Y` as local up; and
- `-Z` as local forward.

The BBTC projectile body basis defined by section 8 uses:

- `+X` as projectile forward;
- `+Y` as projectile right; and
- `+Z` as projectile down.

Therefore the fixed body-to-Cubes-of-Honor-local basis correspondence is:

- BBTC body `+X` maps to Cubes of Honor local `-Z`;
- BBTC body `+Y` maps to Cubes of Honor local `+X`; and
- BBTC body `+Z` maps to Cubes of Honor local `-Y`.

The adapter MAY represent this fixed basis transformation as a constant
quaternion, an equivalent orthonormal three-by-three rotation, or an explicitly
tested basis mapping. It MUST NOT scatter equivalent sign changes or axis
swizzles throughout projectile setup, atmosphere sampling, rendering, or
collision code.

If `q_WC` denotes a Cubes of Honor world-from-local orientation and `q_CB`
denotes the fixed Cubes-of-Honor-local-from-BBTC-body basis rotation, the
initial BBTC world-from-body orientation is conceptually

`q_WB = q_WC * q_CB`

under the Hamilton active-rotation convention frozen in section 5.1.

This composition MUST be verified with basis-vector tests. At minimum, tests
MUST prove that BBTC body forward, right, and down map to the expected Cubes of
Honor directions for identity and representative yaw/pitch orientations.

The initial world-frame projectile velocity SHOULD be constructed from the
physical muzzle-speed magnitude and the transformed BBTC body-forward direction,
rather than by embedding Cubes of Honor camera-axis assumptions in BBTC core
code.

Cubes of Honor matrix functionality remains available to the game for rendering
and scene transforms, but BBTC MUST NOT require `mat4f_t` or any equivalent
host matrix type to integrate projectile rigid-body motion.

## 14. Collision and termination

BBTC does not own Cubes of Honor collision detection.

The external-ballistics system SHOULD expose sufficient state or trajectory
segment information for a host to perform continuous or discrete collision
queries.

A collision reported by the host MAY terminate or otherwise alter the host's
simulation of the projectile, but BBTC MUST NOT acquire a dependency on voxel,
terrain, character, or other game-world geometry.

## 15. Initial implementation sequence

The intended staged implementation is:

1. EB0 — mathematical, state, frame, environment, and integration contracts;
2. EB1 — vacuum six-degree-of-freedom propagation and analytic validation;
3. EB2 — basic aerodynamic relative-air and drag models;
4. EB3 — aerodynamic attitude forces and moments;
5. EB4 — spin-stabilized and gyroscopic effects;
6. EB5 — expanded atmospheric and wind coupling;
7. EB6 — rotating-reference-frame effects where appropriate;
8. EB7 — higher-fidelity Mach-dependent and projectile-specific aerodynamic
   models.

Each stage MUST remain independently testable.

## 16. EB0.1-A acceptance criteria

EB0.1-A is complete when:

- external ballistics is formally defined as independent of internal ballistics;
- the existing generic BBTC library, precision, diagnostic, validation, and
  build rules are explicitly inherited;
- SI-only external-ballistics boundaries are frozen;
- BBTC owns minimal precision-qualified vector and quaternion value types without
  depending on Cubes of Honor math headers;
- BBTC mathematical value types cannot be replaced through host typedef aliases,
  preprocessor configuration, or ABI-changing build switches;
- EB0 requires no public graphics-oriented four-by-four matrix abstraction;
- the reference-frame architecture is right-handed without hard-coded
  geographic axis meanings;
- muzzle-relative/local-origin integration is adopted as the intended Cubes of
  Honor integration strategy;
- the BBTC projectile body frame is frozen as `+X` forward, `+Y` right, and
  `+Z` down;
- world-from-body quaternion semantics and active Hamilton rotation are frozen;
- body-frame angular-velocity semantics and the corresponding quaternion
  differential-equation multiplication order are frozen;
- environment sampling is caller-controlled, position-aware, and time-aware;
- environmental sampling is permitted at numerical derivative sub-stages;
- gravity and planetary/reference-frame rotation are supplied explicitly rather
  than hidden inside the solver;
- numerical integration is separated from aerodynamic force and moment models;
- Cubes of Honor is explicitly responsible for world scale, atmosphere,
  collision, rendering, networking, damage, and gameplay;
- Cubes of Honor integration uses an adapter rather than introducing CoH
  dependencies into BBTC;
- Cubes of Honor retains its existing vector, quaternion, and matrix math while
  crossing the BBTC boundary through explicit value conversions;
- the initial Cubes of Honor integration should use BBTC `double` unless later
  profiling justifies a different supported precision family;
- the fixed Cubes of Honor local-to-BBTC body-basis relationship is documented
  and requires basis-vector verification rather than scattered axis swizzles;
- exact public external-ballistics type names and structure layouts remain
  deferred until their dedicated implementation checkpoints;
- EB0.1-A introduces no external-ballistics public symbol or solver
  implementation; and
- this contract is reviewed and changed from `Draft` to `Accepted` before the
  first EB0 implementation checkpoint is committed.

## 17. EB0.1-B1 mathematical value and rigid-body state foundation

EB0.1-B1 is the first external-ballistics public-code checkpoint. It freezes
the value records required to represent three-dimensional vectors,
orientations, and one six-degree-of-freedom projectile state without yet
introducing vector operations, quaternion operations, state validation,
environment sampling, force or moment models, or numerical integration.

The purpose of this increment is deliberately narrow. Later external-ballistics
layers depend on these records, so their physical meaning and type identity
MUST be established and tested before equations begin to consume them.

### 17.1 Public header structure

The following public headers are introduced:

```text
include/bbtc/external_ballistics.h
include/bbtc/external_ballistics/vector.h
include/bbtc/external_ballistics/quaternion.h
include/bbtc/external_ballistics/state.h
```

`<bbtc/external_ballistics.h>` is the external-ballistics umbrella header and
MUST include the three concrete record headers. `<bbtc/bbtc.h>` MUST include
the external-ballistics umbrella so an ordinary BBTC consumer sees both the
existing API and the new EB0.1-B1 records.

The new headers MUST remain usable from ISO C23 and from the project's supported
C++ public-header compatibility test. No Cubes of Honor header may be required
to parse or use them.

### 17.2 Precision-qualified three-dimensional vectors

The public vector records are:

```c
bbtc_eb_vec3_float_t
bbtc_eb_vec3_double_t
bbtc_eb_vec3_long_double_t
```

Each record contains exactly the named scalar components `x`, `y`, and `z` in
that declaration order, expressed in the record's native scalar family.

The vector record itself carries no unit or coordinate-frame identity. Physical
meaning belongs to the field that contains the vector. For example, a
`position_m` field gives all three components metre semantics, while an
`angular_velocity_body_rad_per_s` field gives all three components body-frame
radians-per-second semantics.

This separation allows the same small vector representation to carry positions,
velocities, angular velocities, forces, moments, gravity, wind, and other
three-component physical quantities without creating one public structure type
for every possible unit.

EB0.1-B1 introduces representation only. No public arithmetic function is
required by this checkpoint.

### 17.3 Precision-qualified quaternions

The public quaternion records are:

```c
bbtc_eb_quat_float_t
bbtc_eb_quat_double_t
bbtc_eb_quat_long_double_t
```

Each record contains the vector components `x`, `y`, and `z`, followed by the
scalar component `w`, all in the matching native scalar family.

The component order matches the convention already frozen by section 5.1 and
is intentionally compatible with straightforward field-wise conversion to the
current Cubes of Honor quaternion representation. Type compatibility or
aliasing is NOT implied by matching component names or order.

A quaternion value record does not, by type alone, guarantee finite components,
unit length, or a physically valid orientation. Those requirements belong to
the future public state-validation contract. In particular, an all-zero
quaternion is representable but is not a valid orientation.

EB0.1-B1 introduces no public quaternion multiplication, normalization,
conjugation, vector-rotation, or interpolation function.

### 17.4 Precision-qualified rigid-body state

The first public six-degree-of-freedom state records are:

```c
bbtc_eb_rigid_body_state_float_t
bbtc_eb_rigid_body_state_double_t
bbtc_eb_rigid_body_state_long_double_t
```

Each state MUST contain the following fields:

```text
orientation_world_from_body
position_m
velocity_m_per_s
angular_velocity_body_rad_per_s
time_s
```

The declaration order above is frozen for EB0.1-B1. The quaternion is declared
first, followed by the three vector-valued members and then the scalar time.
This ordering keeps the largest composite member first and groups equal-sized
vector records together without changing any physical semantics.

`orientation_world_from_body` is the active world/reference-from-projectile-body
rotation defined by sections 5.1, 7, and 12. It is stored in the matching
`bbtc_eb_quat_*_t` type.

`position_m` is the projectile center-of-mass position in metres in the active
world/reference frame. In the intended Cubes of Honor adapter this position is
relative to the muzzle-local integration origin described by section 6.

`velocity_m_per_s` is the projectile center-of-mass translational velocity in
metres per second in the active world/reference frame.

`angular_velocity_body_rad_per_s` is the projectile angular-velocity vector in
radians per second expressed in the BBTC body frame defined by section 8.

`time_s` is simulation time in seconds measured from the external-ballistics
initial state.

The state record deliberately stores translational quantities in the active
world/reference frame while storing angular velocity in the body frame. Future
equations and validation MUST preserve that distinction explicitly.

A zero-initialized state is useful as deterministic storage but is not, by
itself, a valid projectile state because its quaternion is the all-zero
quaternion. EB0.1-B1 MUST NOT add an implicit identity-orientation fallback.

### 17.5 Ownership, ABI, and conversion rules

All EB0.1-B1 records are plain caller-owned values. They contain no pointers,
dynamic storage, hidden ownership, allocator state, reference counts, or host
application handles.

The records MUST NOT contain `vec3f_t`, `quatf_t`, `mat4f_t`, or another Cubes
of Honor type. The Cubes of Honor adapter performs explicit field-wise
conversion as required by sections 5.2 and 13.1.

No public alignment override is introduced by EB0.1-B1. Natural ISO C object
layout is used. The project MUST NOT freeze one universal byte size for these
records because scalar size and alignment are implementation properties,
especially for `long double`.

Tests MAY verify coherent layout properties on the current platform, but public
correctness MUST NOT depend on a particular padding pattern beyond the frozen
declaration and scalar-family semantics.

### 17.6 Deliberately deferred behavior

EB0.1-B1 does NOT define:

- vector arithmetic functions;
- quaternion arithmetic functions;
- quaternion normalization tolerance;
- rigid-body-state validation functions;
- environment-provider records or callbacks;
- gravity or planetary-rotation records;
- projectile mass, dimensions, or inertia records;
- force or moment accumulation;
- aerodynamic coefficients;
- numerical derivatives;
- an integration stepper; or
- Cubes of Honor adapter source code.

Those behaviors require their own reviewed contracts. Representation MUST be
established before algorithms begin assigning additional semantics to it.

## 18. Acceptance criteria for EB0.1-B1

EB0.1-B1 is complete when:

- the exact precision-qualified vector, quaternion, and rigid-body-state type
  names in section 17 are public through `<bbtc/external_ballistics.h>` and
  `<bbtc/bbtc.h>`;
- each vector family uses native `float`, `double`, or `long double` components
  named `x`, `y`, and `z` without routing representation through another scalar
  family;
- each quaternion family uses native components named `x`, `y`, `z`, and `w`
  with `w` as the scalar component and no implicit validity guarantee;
- each rigid-body state contains the exact fields and declaration order frozen
  by section 17.4 using matching precision-qualified vector and quaternion
  records;
- state documentation explicitly freezes world/reference-frame position and
  velocity, world-from-body orientation, body-frame angular velocity, and
  seconds-from-initial-state time semantics;
- a zero-initialized state is documented as representable storage rather than a
  silently valid identity-oriented projectile;
- the records contain no pointer, allocation, host-engine, or Cubes of Honor
  ownership state;
- no public matrix type or host math dependency is introduced;
- C23 compile-time tests verify native scalar-family field types;
- the C++ public-header test verifies the same native type relationships and
  nested state-member types;
- the independent CMake consumer can construct and read a native-double
  external-ballistics state through `<bbtc/bbtc.h>`;
- CMake exposes every new public header through the existing `bbtc` /
  `bbtc::bbtc` target without adding a new mandatory dependency;
- the existing internal-ballistics, diagnostics, precision, consumer, and C++
  tests remain unchanged in behavior and continue to pass;
- strict compiler and sanitizer gates applicable to the repository continue to
  pass;
- EB0.1-B1 adds representation and tests only, with no vector/quaternion
  arithmetic, validation, environment, aerodynamics, integration, or Cubes of
  Honor adapter implementation; and
- contract version 0.1.1 is reviewed and changed from `Draft` to `Accepted`
  before the EB0.1-B1 public-record implementation is committed.

## 19. EB0.1-B2 mathematical operations and state validation

EB0.1-B2 establishes the mathematical correctness layer required by later
external-ballistics dynamics. It adds a deliberately small internal
three-dimensional vector and quaternion operation set plus public validation of
the rigid-body state introduced by EB0.1-B1.

This checkpoint does NOT introduce projectile physical properties, atmosphere
sampling, force or moment models, derivatives of the rigid-body state, or a
numerical integrator. Its purpose is to make the coordinate and quaternion
machinery trustworthy before physical equations depend on it.

### 19.1 Legacy reconstruction constraints

The pre-rewrite BBTC external-ballistics implementation is a research reference,
not a normative source for the reconstructed API or conventions.

Useful legacy concepts MAY be reimplemented after independent verification,
including Hamilton quaternion multiplication, quaternion conjugation,
quaternion-vector rotation, vector cross products, and normalization.

Legacy behavior MUST NOT override the conventions already frozen by this
contract. In particular:

- the legacy orientation derivative used the multiplication order
  `omega_quat * q`;
- the reconstructed world-from-body orientation with body-frame angular
  velocity requires the later derivative contract to use `q * omega_body_quat`;
- the legacy quaternion normalizer silently left sufficiently small
  quaternions unchanged;
- the reconstructed implementation MUST report normalization failure rather
  than silently preserving or replacing an invalid quaternion; and
- no vector operation may combine operands expressed in different coordinate
  frames merely because their storage representations match.

EB0.1-B2 does not yet implement the quaternion orientation derivative. The
legacy multiplication-order discrepancy is recorded here so the later dynamics
checkpoint MUST test the frozen section 12 convention independently.

### 19.2 Internal mathematics boundary

The vector and quaternion operations introduced by EB0.1-B2 are implementation
support for BBTC physics and are NOT added to the public external-ballistics
API in this checkpoint.

The internal operation set MUST have native `float`, `double`, and
`long double` implementations. A family MUST NOT route arithmetic through
another scalar family.

The implementation MAY use a private internal header shared by BBTC source
files and dedicated internal tests. Such declarations are not public ABI and
MUST NOT be installed or included by `<bbtc/external_ballistics.h>`.

The internal operation set MUST NOT allocate dynamic storage, perform file I/O,
write diagnostics to standard streams, or depend on Cubes of Honor math types.

### 19.3 Internal three-dimensional vector operations

EB0.1-B2 MUST provide internal precision-qualified operations sufficient for:

- component-wise addition;
- component-wise subtraction;
- scalar multiplication;
- dot product;
- right-handed cross product;
- squared Euclidean norm;
- Euclidean norm; and
- normalization.

The right-handed cross product MUST satisfy the canonical basis relationships:

```text
+X cross +Y = +Z
+Y cross +Z = +X
+Z cross +X = +Y
```

and reversing either operand MUST reverse the result.

Norm and normalization implementations SHOULD avoid unnecessary overflow or
underflow where a standard-library scaling operation such as the appropriate
`hypot` family can provide a more robust result.

Vector normalization MUST be fail-closed. For the internal status-returning
normalization operation:

- a null input or output pointer returns `BBTC_STATUS_INVALID_ARGUMENT`;
- a NaN component returns `BBTC_STATUS_NAN_INPUT`;
- an infinite component returns `BBTC_STATUS_NONFINITE_INPUT`;
- a finite zero-length vector returns `BBTC_STATUS_OUTSIDE_DOMAIN`; and
- a finite nonzero vector produces a unit vector and
  `BBTC_STATUS_SUCCESS`.

On every failure for which a nonnull output pointer is available, the output
record MUST be cleared to all-zero components.

### 19.4 Internal quaternion operations

EB0.1-B2 MUST provide internal precision-qualified operations sufficient for:

- identity-quaternion construction;
- Hamilton multiplication;
- conjugation;
- squared Euclidean norm;
- Euclidean norm;
- normalization; and
- active rotation of a three-dimensional vector by a unit quaternion.

Quaternion multiplication MUST use the Hamilton product and MUST preserve
operand order. Quaternion multiplication is not commutative, and tests MUST
include at least one case for which `q1 * q2` and `q2 * q1` produce distinct
rotations.

The identity quaternion is:

```text
(x, y, z, w) = (0, 0, 0, 1)
```

Quaternion conjugation negates `x`, `y`, and `z` while preserving `w`.

For a unit quaternion `q` and vector `v`, active vector rotation MUST be
equivalent to:

`q * (0, v) * conjugate(q)`.

An optimized algebraically equivalent vector-rotation formula MAY be used by
the implementation, but tests MUST compare representative optimized results
against the explicit Hamilton-product definition.

Quaternion normalization MUST be fail-closed. For the internal
status-returning normalization operation:

- a null input or output pointer returns `BBTC_STATUS_INVALID_ARGUMENT`;
- a NaN component returns `BBTC_STATUS_NAN_INPUT`;
- an infinite component returns `BBTC_STATUS_NONFINITE_INPUT`;
- a finite zero-length quaternion returns `BBTC_STATUS_OUTSIDE_DOMAIN`; and
- a finite nonzero quaternion produces a unit quaternion and
  `BBTC_STATUS_SUCCESS`.

Normalization MUST NOT silently substitute the identity quaternion for an
invalid input.

On every failure for which a nonnull output pointer is available, the output
quaternion MUST be cleared to all-zero components.

### 19.5 Public rigid-body-state validation

EB0.1-B2 introduces the following public functions:

```c
bbtc_status_e
bbtc_eb_rigid_body_state_validate_float(
    const bbtc_eb_rigid_body_state_float_t* state
);

bbtc_status_e
bbtc_eb_rigid_body_state_validate_double(
    const bbtc_eb_rigid_body_state_double_t* state
);

bbtc_status_e
bbtc_eb_rigid_body_state_validate_long_double(
    const bbtc_eb_rigid_body_state_long_double_t* state
);
```

These functions validate caller-owned state without modifying it.

Validation MUST inspect:

- all four orientation-quaternion components;
- all three position components;
- all three translational-velocity components;
- all three body-angular-velocity components; and
- simulation time.

Finite position, translational velocity, and angular velocity may otherwise
have any sign or magnitude representable by the selected scalar family.

`time_s` MUST be greater than or equal to zero. Negative zero is accepted as
zero by the ordinary floating-point comparison semantics.

The orientation quaternion MUST be finite, nonzero, and sufficiently close to
unit length as defined by section 19.6.

The validator MUST NOT normalize, repair, clamp, replace, or otherwise mutate a
supplied state.

### 19.6 Orientation unit-norm acceptance tolerance

Public state validation compares the squared quaternion norm against one:

`abs(norm_squared - 1) <= tolerance`.

For EB0.1-B2, the acceptance tolerance for every scalar family is:

`64 * FLT_EPSILON`.

This common interoperability floor is intentional. Cubes of Honor currently
uses float-oriented quaternion math while the intended first BBTC integration
uses the native-double family. A quaternion that was normalized in float and
then converted component-by-component to double MUST NOT be rejected merely
because the double family can represent a much tighter normalization residual.

The tolerance is a validation boundary, not the arithmetic precision used by
the double or long-double solver families. Internal normalization and later
integration continue to use the native scalar family.

The validator MUST compute the norm in a manner that does not turn ordinary
finite near-unit inputs into false overflow or underflow failures.

A quaternion outside this tolerance returns `BBTC_STATUS_OUTSIDE_DOMAIN`.

This tolerance MAY be revised only through an explicit contract revision with
tests demonstrating the interoperability and numerical consequences.

### 19.7 Validation precedence

When more than one invalid condition exists in one rigid-body state, public
validation MUST apply the following deterministic precedence:

1. a null state pointer returns `BBTC_STATUS_INVALID_ARGUMENT`;
2. if any inspected scalar is NaN, return `BBTC_STATUS_NAN_INPUT`;
3. otherwise, if any inspected scalar is positive or negative infinity, return
   `BBTC_STATUS_NONFINITE_INPUT`;
4. otherwise, if `time_s` is negative, return
   `BBTC_STATUS_OUTSIDE_DOMAIN`;
5. otherwise, if the orientation quaternion is zero-length or outside the
   unit-norm acceptance tolerance, return `BBTC_STATUS_OUTSIDE_DOMAIN`;
6. otherwise return `BBTC_STATUS_SUCCESS`.

The NaN and infinity scans MUST cover the complete state before domain
conditions are evaluated. This prevents member declaration order from changing
the status reported for a multiply-invalid state.

### 19.8 Convention and interoperability tests

EB0.1-B2 tests MUST establish the mathematical conventions independently of
later ballistic behavior.

At minimum, tests MUST verify:

- right-handed cross-product basis identities and operand reversal;
- exact identity-quaternion behavior;
- Hamilton multiplication order with noncommuting rotations;
- conjugation;
- normalization success for representative nonunit finite values;
- normalization failure for zero, NaN, and infinity;
- active 90-degree basis rotations about each canonical positive axis;
- equivalence of `q` and `-q` as rotations;
- agreement between the optimized quaternion-vector rotation, if used, and the
  explicit `q * v * conjugate(q)` reference form;
- a unit quaternion passes rigid-body-state validation;
- zero orientation fails state validation;
- a materially nonunit orientation fails state validation;
- a quaternion within the section 19.6 tolerance passes validation;
- negative time fails validation;
- arbitrary finite signed position, velocity, and angular velocity are accepted;
- deterministic NaN-before-infinity-before-domain validation precedence; and
- all three precision families execute their own native arithmetic paths.

The Cubes of Honor basis relationship from section 13.1 MUST also be exercised
as a mathematical reference test. The unit quaternion

```text
(x, y, z, w) = (0.5, 0.5, -0.5, 0.5)
```

represents one valid active Cubes-of-Honor-local-from-BBTC-body basis rotation
under the frozen convention and MUST map:

```text
BBTC body +X -> Cubes of Honor local -Z
BBTC body +Y -> Cubes of Honor local +X
BBTC body +Z -> Cubes of Honor local -Y
```

Its negation MUST produce the same three rotated basis vectors.

This constant is a convention test vector, not a requirement that the future
Cubes of Honor adapter store or hard-code one particular quaternion sign.

### 19.9 Deliberately deferred behavior

EB0.1-B2 does NOT define or implement:

- quaternion orientation derivatives;
- rigid-body derivatives;
- projectile mass or inertia;
- aerodynamic reference geometry;
- environment samples or provider callbacks;
- gravity or rotating-reference-frame data;
- force or moment accumulation;
- aerodynamic coefficients or drag;
- RK4 or another numerical integrator; or
- Cubes of Honor adapter source code.

The later dynamics checkpoint MUST specifically test the section 12
`q_WB * omega_B_quat` orientation-derivative order rather than copying the
pre-rewrite `omega_quat * q` implementation.

## 20. Acceptance criteria for EB0.1-B2

EB0.1-B2 is complete when:

- the contract version is 0.1.2 and the checkpoint is reviewed and changed from
  `Draft` to `Accepted` before implementation is committed;
- native float, double, and long-double internal vector operations satisfy the
  section 19.3 semantics;
- native float, double, and long-double internal quaternion operations satisfy
  the section 19.4 semantics;
- internal vector and quaternion normalization are status-returning,
  fail-closed, and clear nonnull outputs on failure;
- no invalid quaternion is silently converted to identity;
- public precision-qualified rigid-body-state validation functions exist with
  the exact names in section 19.5;
- state validation does not modify caller-owned state;
- state validation uses the deterministic precedence in section 19.7;
- state validation enforces the section 19.6 quaternion unit-norm tolerance
  without reducing double or long-double arithmetic to float;
- the legacy quaternion multiplication-order ambiguity is explicitly prevented
  from defining reconstructed behavior;
- direct mathematical tests cover right-handed vector algebra, Hamilton
  quaternion composition, active rotations, `q`/`-q` equivalence, and the
  Cubes of Honor basis mapping;
- C, C++, and independent-consumer tests exercise the public validation API;
- existing BBTC internal-ballistics, diagnostics, precision, consumer, and
  public-header tests continue to pass;
- strict compiler and sanitizer gates applicable to the repository continue to
  pass; and
- EB0.1-B2 introduces no projectile-properties, environment, aerodynamic,
  derivative, integrator, or Cubes of Honor adapter implementation.
